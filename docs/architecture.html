Core Architecture & Extensibility

A systems-level guide on the internal mechanics of Workflow Forge. Learn how to write patches, create custom tools, optimize the async core, or register plugins.

1. Workspace Decoupling & Layering

Workflow Forge is designed around strict architectural layering. The workspace partitions responsibilities into clean, isolated crates, keeping dependencies modular and highly testable.

graph TD Facade[workflow-forge Facade] ExtUtil[util extension] ExtData[data extension] ExtHttp[http extension] ExtTab[tabular extension] ExtSftp[sftp extension] Core[workflow-forge-core] Facade --> ExtUtil Facade --> ExtData Facade --> ExtHttp Facade --> ExtTab Facade --> ExtSftp ExtUtil --> Core ExtData --> Core ExtHttp --> Core ExtTab --> Core ExtSftp --> Core style Facade fill:#4f46e5,stroke:#818cf8,stroke-width:2px,color:#fff style Core fill:#1e1b4b,stroke:#4f46e5,stroke-width:2px,color:#fff
  • `crates/core`: The heart of the system. Contains all spec types, static DAG validation rules, JSONPath mappings, profile compiling, and `BlobStore` interfaces. It is completely isolated and has zero awareness of downstream extensions.
  • `crates/extensions/*`: Independent sibling crates. Each crate implements the `Task` trait for a specific namespace, defining its schemas and isolated unit/integration tests.
  • `crates/forge`: Facade crate that exposes feature flags (such as `util`, `data`, `http`, `tabular`, `sftp`). This is the primary dependency embedded by hosting applications.

2. Traits & System Abstractions

Extensibility is managed by a set of core traits. By implementing these traits, developers can customize binary storage, inject environment credentials, or add new tasks. 

use async_trait::async_trait;
use serde_json::Value;

// 1. Task interface
#[async_trait]
pub trait Task: Send + Sync {
    /// Returns the static manifest of the task (identity, description, schemas)
    fn manifest(&self) -> &TaskManifest;

    /// Executes the task logic asynchronously
    async fn execute(&self, ctx: &WorkflowContext, input: WorkflowData) -> WorkflowResult;
}

// 2. Streamed Binary Storage interface
#[async_trait]
pub trait BlobStore: Send + Sync {
    /// Streams binary data into local storage, returning a unique string reference
    async fn put(&self, name: &str, reader: BoxBlobReader) -> Result;

    /// Streams binary data out of storage using its UUID
    async fn get(&self, id: &str) -> Result;

    /// Deletes all files associated with the active execution run
    async fn cleanup(&self) -> Result<(), BlobError>;
}

// 3. Secrets provider interface
pub trait SecretsProvider: Send + Sync {
    /// Resolves sensitive keys (api tokens, private keys) from secure backends
    fn get_secret(&self, key: &str) -> Option;
}

3. Static DAG Validation Engine

When a workflow JSON is loaded, the WorkflowExecutor::new constructor compiles and validates its graph structure before running any tasks.

Algorithm: Depth-First Cycle Checks

The compiler constructs an adjacency list representation of the edges. It walks the graph using a Depth-First Search (DFS) algorithm with a recursion stack to identify back-edges. If any back-edge is found, compilation is aborted with a GraphCycleDetected diagnostic error, protecting the execution loop from infinite loops.

Structural Orphan Scanning

A verification pass walks forward from the start node and backward from all end nodes. Any node left unvisited is marked as an orphan. This catches disconnected steps during design time, raising OrphanNodes errors before deployment.

Edge Integrity & Join Constraints

The compiler validates that all transition arrows connect to declared node IDs. It also checks that:

  • Join gateways have at least two incoming paths.
  • No incoming path to a Join gateway originates from a conditional branch of an exclusive gateway, preventing starved join deadlocks.

4. Async Tokio Scheduler & Execution Loop

Once compiled, the engine traverses the validated graph. It walks down concurrent execution paths in parallel using Tokio's async task pool.

Execution Phase Pipeline

  1. Input Mapping Evaluation: Resolves the node's input selectors against the shared execution context, constructing the task's final input JSON object.
  2. Runtime Schema Validation: Validates the mapped input object against the task's declared input_schema. If validation fails, execution halts immediately.
  3. Task Execution: Invokes the task's execute method, passing the thread-safe WorkflowContext (which provides access to the BlobStore and SecretsProvider).
  4. Output Validation & Mutation: Validates the output returned by the task against its output_schema. It then mutates the global context, publishing the result to $.nodes.<id>.output using thread-safe write locks.
  5. Forking & Concurrency Scheduling: Determines outgoing edges. If multiple paths diverge, it spawns concurrent Tokio task futures using `tokio::spawn` or concurrent join structures to process paths in parallel.

5. Error Handling & Panic Isolation Boundaries

In a production orchestrator, custom task failures or panics must not crash the hosting process. Workflow Forge isolates failures at the node boundary:

Standard Task Failures

If a task returns an `Err(TaskError)` (e.g. timeout, network issue, or failed validation), the engine stops the standard path. If an on: "error" transition is defined on the edge, the executor writes a structured error to $.nodes.<id>.error and routes execution down that path.

Caught Rust Panics

If a task panics (e.g. due to an index out of bounds), the engine catches the panic using FutureExt::catch_unwind. This keeps the hosting process safe. The node is marked as failed, and execution is routed along a declared on: "panic" edge.

6. Writing Custom Tasks (Rust Implementation Guide)

Custom tasks are implemented in Rust. We recommend using the schemars crate to automatically generate JSON Schema definitions from your Rust structures, ensuring your task parameters remain in sync with your code: 

use workflow_forge::prelude::*;
use async_trait::async_trait;
use schemars::JsonSchema;
use serde::{Deserialize, Serialize};

// 1. Declare expected inputs
#[derive(Debug, Serialize, Deserialize, JsonSchema)]
pub struct RiskInput {
    pub value_to_check: f64,
    pub threshold: f64,
}

// 2. Declare generated outputs
#[derive(Debug, Serialize, Deserialize, JsonSchema)]
pub struct RiskOutput {
    pub risk_rating: String,
    pub above_limit: bool,
}

// 3. Create task struct
pub struct RiskScoreTask {
    manifest: TaskManifest,
}

impl RiskScoreTask {
    pub fn new() -> Self {
        // Automatically compile JSON Schemas from structs
        let input_schema = schemars::schema_for!(RiskInput);
        let output_schema = schemars::schema_for!(RiskOutput);

        let manifest = TaskManifest::new(
            "risk.score",
            "Evaluate numbers against a custom threshold"
        )
        .with_input_schema(serde_json::to_value(input_schema).unwrap())
        .with_output_schema(serde_json::to_value(output_schema).unwrap());

        Self { manifest }
    }
}

// 4. Implement execute logic
#[async_trait]
impl Task for RiskScoreTask {
    fn manifest(&self) -> &TaskManifest {
        &self.manifest
    }

    async fn execute(&self, _ctx: &WorkflowContext, input: WorkflowData) -> WorkflowResult {
        // Safe deserialization (payload is already validated against input_schema)
        let args: RiskInput = serde_json::from_value(input.0)?;

        let above_limit = args.value_to_check > args.threshold;
        let risk_rating = if above_limit {
            "critical".to_string()
        } else {
            "standard".to_string()
        };

        let result = RiskOutput { risk_rating, above_limit };
        Ok(WorkflowData(serde_json::to_value(result)?))
    }
}

7. Embedding & Compiling the Engine

Once you've implemented your custom tasks, register them with the TaskRegistry, load your workflow JSON, and compile your executor: 

use workflow_forge::prelude::*;
use std::sync::Arc;

#[tokio::main]
async fn main() -> Result<(), Box> {
    // 1. Initialize empty Registry
    let mut registry = TaskRegistry::new();

    // Register custom tasks
    registry.register(Arc::new(RiskScoreTask::new()));

    // Register official core extensions
    workflow_forge_ext_http::register(&mut registry);
    workflow_forge_ext_data::register(&mut registry);

    // 2. Parse workflow definition from JSON
    let workflow_json = r#"{
        "spec": "1.0",
        "name": "risk-pipeline",
        "version": "1.0.0",
        "nodes": [
            { "id": "start", "kind": "start" },
            {
                "id": "risk",
                "kind": "task",
                "task": "risk.score",
                "input": { "value_to_check": 95.0, "threshold": 80.0 }
            },
            { "id": "end", "kind": "end" }
        ],
        "edges": [
            { "from": "start", "to": "risk" },
            { "from": "risk", "to": "end" }
        ]
    }"#;

    let definition = serde_json::from_str(workflow_json)?;

    // 3. Compile and validate DAG
    let executor = WorkflowExecutor::new(definition, registry)
        .map_err(|errors| format!("Compilation failed: {:?}", errors))?;

    // 4. Run to completion
    let result = executor.run(WorkflowData(serde_json::json!({}))).await?;
    println!("Workflow result: {}", result.0);

    Ok(())
}
