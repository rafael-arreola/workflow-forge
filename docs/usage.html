workflow-forge — User Manual

The complete guide to designing and running declarative workflows with workflow-forge, from zero to production. This manual targets workflow authors and integrators: people who write workflow documents and embed the engine in their applications. If you want to extend or maintain the engine itself, read the Infrastructure Manual.

1. Introduction

workflow-forge is a Rust library for executing declarative workflows defined as JSON documents. A workflow is a directed acyclic graph (DAG) of nodes connected by edges; the engine walks the graph asynchronously on Tokio, resolving data between nodes with JSONPath mappings.

Design principles

  • Declarative first. A workflow is data, not code. It can be stored, versioned, validated, and rendered without executing anything.
  • Fail at build time, not at runtime. The executor validates the entire document when it is constructed: graph structure, cycles, reachability, gateway coherence, task registration, JSON Schemas, subworkflow resolution. If WorkflowExecutor::new succeeds, the document is structurally sound.
  • Strict data isolation. Nodes never call each other. They read from and write to a shared, concurrency-safe state document via immutable JSONPath mappings.
  • Payloads by reference. Large binaries (files, spreadsheets, archives) never travel inline in JSON. They travel as $blob references backed by a per-execution store that is cleaned up automatically.
  • Defensive resilience. Retries with backoff, per-attempt timeouts, error-routing edges, and panic isolation: a buggy task extension cannot bring down the host process.

2. Getting Started

Installation

# Cargo.toml
[dependencies]
workflow-forge = { version = "0.1", features = ["full"] }
tokio = { version = "1", features = ["full"] }
serde_json = "1"

Feature flags select which extensions are compiled in:

FeatureEnables
defaultutil, data, http
fulleverything: util, data, http, tabular, sftp
util / data / http / tabular / sftpeach extension individually

Your first workflow

use workflow_forge::prelude::*;
use serde_json::json;

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    // 1. A registry with every feature-enabled extension task pre-registered
    let registry = workflow_forge::default_registry();

    // 2. The workflow document (usually loaded from a file or database)
    let workflow: WorkflowDefinition = serde_json::from_value(json!({
        "spec": "1.0",
        "name": "hello",
        "version": "0.1.0",
        "nodes": [
            { "id": "start", "kind": "start" },
            { "id": "greet", "kind": "task", "task": "data.template",
              "input": {
                  "template": "Hello, {who}!",
                  "values": { "who": "$.trigger.name" }
              }
            },
            { "id": "end", "kind": "end" }
        ],
        "edges": [
            { "from": "start", "to": "greet" },
            { "from": "greet", "to": "end" }
        ]
    }))?;

    // 3. Build the executor — this validates everything up front
    let executor = WorkflowExecutor::new(workflow, registry)
        .map_err(|errors| format!("{errors:?}"))?;

    // 4. Run it with a trigger payload
    let result = executor.run(WorkflowData(json!({ "name": "Ada" }))).await?;
    assert_eq!(*result, json!("Hello, Ada!"));
    Ok(())
}
The two-phase contract. Building the executor (WorkflowExecutor::new / builder()) returns Err(Vec<WorkflowError>) with every definition problem found — not just the first one. Running it (executor.run(trigger)) returns a single WorkflowResult. Definition errors belong to build time; data errors belong to runtime.

3. The Workflow Document

A workflow definition is a JSON object with the following top-level fields:

FieldTypeRequiredDescription
specstringno (default "1.0")Spec version this document conforms to. The engine rejects unsupported versions (UNSUPPORTED_SPEC).
idstringnoStable identifier of the workflow. Assigned if absent.
namestringyesHuman-readable name. Also the lookup key for subworkflow references.
versionstringyesSemantic version of the document itself.
tasksarraynoLocal task profiles: named, pre-configured instances of registered tasks, visible only to this document.
workflowsarraynoInline subworkflow definitions, referenced by name from subworkflow nodes. Take precedence over the shared registry.
nodesarrayyesThe graph nodes. Each has a unique id and a kind discriminator.
edgesarraynoDirected control-flow edges between nodes.

Structural rules (enforced at build time)

  • Exactly one start node, at least one end node.
  • start has no incoming edges; end has no outgoing edges.
  • Node ids are unique; every edge references existing nodes.
  • The graph is acyclic and every node is reachable from start.
  • Gateways are coherent (see gateway): every exclusive branch has a matching labeled edge and vice versa; parallel needs ≥ 2 outgoing edges; join needs ≥ 2 normal incoming edges.

4. Execution Context & Data Flow

Every execution maintains a single shared state document. All mappings and conditions are resolved against it:

{
  "trigger":  { ... },               // the input payload passed to run()
  "nodes": {
    "<node-id>": {
      "output": { ... },             // published when the node completes
      "error":  { code, message }    // published when a node fails and is error-routed
    }
  },
  "workflow": {
    "id": "...", "name": "...", "version": "...",
    "execution_id": "0197a3f1-..."   // UUID v7, unique per run
  }
}
  • $.trigger — the initial input, validated against the start node's schema if one is declared.
  • $.nodes.<id>.output — the result of every node that has already executed. This is how downstream nodes consume upstream results.
  • $.nodes.<id>.error — present only when a node failed and the flow continued through an on: error edge.
  • $.workflow — metadata, useful for templating ids into requests or logs.

The state document is thread-safe: parallel gateway branches read and write concurrently without races. Data flows exclusively through the document — there is no other side channel between nodes.

The "token" — implicit data flow

Besides the state document, each node receives the output of its predecessor as an implicit token. Some constructs use it as a default: an end node without output returns the predecessor's output; a subworkflow node without input passes the predecessor's output to the child as its trigger.

5. Mappings ($.)

Mappings are how a node's input (and a foreach's items, and an end's output) pull data from the context. The rules of spec 1.0:

ValueBehavior
String starting with $.Resolved as JSONPath against the state document. The whole string is the path; partial interpolation is not supported (use data.template for that).
String starting with $$.Escape: produces the literal $. prefix without resolving. "$$.price" → the string "$.price".
Any other string, number, bool, nullLiteral, copied as-is.
Objects and arraysWalked recursively; every nested string follows the same rules.
"input": {
  "url": "$.trigger.api_base",                 // resolved from context
  "method": "POST",                            // literal
  "body": {
    "user": "$.nodes.fetch.output.body.name",  // nested resolution
    "flags": [true, "$.nodes.fetch.output.status"]
  }
}
A path that does not resolve is an error (MAPPING_PATH_NOT_FOUND), because in an input it is almost always a definition bug. If a value is genuinely optional, prepare it with a data.* node first (e.g. data.cast with a default op). Paths are singular: the first match wins; wildcards are not supported in mappings.

6. Node Reference

Every node is { "id": "...", "kind": "..." , ...kind-specific fields }. The kind vocabulary is fixed by the spec: start, end, task, foreach, gateway, subworkflow.

start — the entry point

FieldTypeDescription
schemaJSON SchemaOptional. Validates the trigger payload; the run fails with SCHEMA_VALIDATION_FAILED before any node executes if it does not conform.
defaultsobjectOptional. Key/value defaults merged into the trigger (useful for injecting configuration constants).
{ "id": "start", "kind": "start",
  "schema": { "type": "object", "required": ["order_id"] },
  "defaults": { "region": "us-east" } }

end — terminal result

FieldTypeDescription
statusstring"success" (default), "error", "cancelled", or any custom string. Lets callers distinguish which terminal path was taken.
outputmappingOptional. The workflow's final result, resolved against the context. Omitted → the predecessor's output is the result.
schemaJSON SchemaOptional. Validates the final result (OUTPUT_SCHEMA_VALIDATION_FAILED).
{ "id": "end", "kind": "end",
  "output": { "order_id": "$.nodes.create.output.body.id",
              "status_code": "$.nodes.create.output.status" } }

A workflow may have several end nodes (one per branch). If execution finishes without reaching any of them, it fails with NO_OUTPUT.

task — invoke a registered task

FieldTypeDescription
taskstringRequired. Namespaced task id, e.g. "http.request" or a profile id. Must be registered (TASK_NOT_FOUND at build otherwise).
inputmappingOptional. Input mapping resolved against the context. The resolved value is validated against the task's input_schema (TASK_INPUT_INVALID).
retryobjectOptional retry policy (below).
timeout_msintegerOptional. Maximum duration per attempt in milliseconds. Exceeding it produces TASK_TIMEOUT, which is retryable.

Retry policy

FieldTypeDescription
maxintegerRequired. Maximum retries after the initial attempt (so max: 2 means up to 3 attempts).
backoffstring"exponential" (default): initial_ms × 2^(attempt−1) · "linear": initial_ms × attempt · "fixed": constant initial_ms.
initial_msintegerBase delay before the first retry. Default 500.
{ "id": "create", "kind": "task", "task": "http.request",
  "input": { "url": "$.trigger.endpoint", "method": "POST",
             "body": "$.nodes.adapt.output", "fail_on_error_status": true },
  "retry": { "max": 3, "backoff": "exponential", "initial_ms": 250 },
  "timeout_ms": 10000 }

foreach — iterate an array with a task

Runs one task invocation per array element. Each element is the direct input of the task — reshape elements beforehand with data.map if needed.

FieldTypeDescription
taskstringRequired. Task (or profile) executed once per element.
itemsmappingRequired. Must resolve to an array (FOREACH_ITEMS_NOT_ARRAY otherwise).
concurrencyintegerElements in flight simultaneously. Default 1 (sequential). Must be ≥ 1 (FOREACH_INVALID_CONCURRENCY at build).
throttle_msintegerDelay between element starts — a rate limiter to avoid hammering downstream systems. Default 0.
on_item_errorstring"fail" (default): the first element failure cancels the rest and fails the node. "collect": run everything; the node never fails because of element errors.
retry, timeout_msSame semantics as task, applied per element.

Output shape — with on_item_error: "fail" the output is the array of element outputs, in order. With "collect":

{
  "ok":     [ ...outputs of successful elements... ],
  "failed": [ { "index": 1, "item": { ... }, "error": { "code": "...", "message": "..." } } ]
}
{ "id": "batch", "kind": "foreach",
  "task": "acme.create_shipment",
  "items": "$.nodes.adapt.output",
  "concurrency": 4,
  "throttle_ms": 100,
  "on_item_error": "collect",
  "retry": { "max": 2, "initial_ms": 200 } }

gateway — control flow

Three BPMN-style gateway kinds, selected with the gateway field:

exclusive — if/else routing

Evaluates branches in order; the first branch whose when condition holds wins, and execution follows the outgoing edge whose label equals the branch's edge. A branch with "else": true (at most one) wins when nothing else matched. No match and no else → the run fails with NO_BRANCH_MATCHED.

{ "id": "verdict", "kind": "gateway", "gateway": "exclusive",
  "branches": [
    { "when": { "path": "$.nodes.check.output.status", "eq": 200 }, "edge": "healthy" },
    { "when": { "path": "$.nodes.check.output.status", "gte": 500 }, "edge": "outage" },
    { "else": true, "edge": "degraded" }
  ] }
// edges: { "from": "verdict", "to": "...", "label": "healthy" }, etc.

Build-time coherence checks: every branch needs a matching labeled edge (GATEWAY_BRANCH_WITHOUT_EDGE), every labeled edge needs a branch (GATEWAY_EDGE_WITHOUT_BRANCH), at most one else (GATEWAY_MULTIPLE_ELSE), branches need when or else (GATEWAY_BRANCH_WITHOUT_WHEN), and an exclusive gateway must declare branches (GATEWAY_NO_BRANCHES).

parallel — fan-out

All outgoing edges execute concurrently. Requires at least 2 outgoing edges (PARALLEL_TOO_FEW_OUTPUTS). Declares no branches (GATEWAY_BRANCHES_IGNORED).

join — fan-in

Waits for all incoming normal-flow branches (wait-all, fail-fast: if any branch fails definitively, the join fails). Requires at least 2 incoming edges (JOIN_TOO_FEW_INPUTS). If the run ends while a join is still waiting for branches that can no longer arrive, it fails with JOIN_INCOMPLETE. Error edges may not target a join (ERROR_EDGE_TO_JOIN).

{ "id": "fan",  "kind": "gateway", "gateway": "parallel" },
{ "id": "join", "kind": "gateway", "gateway": "join" }

subworkflow — compose workflows

FieldTypeDescription
workflowstringRequired. Name of the child workflow. Resolved against the document's inline workflows section first, then the shared WorkflowRegistry.
inputmappingOptional. Becomes the child's trigger. Omitted → the predecessor's output is the trigger.

The child's final output becomes the node's output. Failures route like any task: a child failure follows on: error edges, a panic inside the child follows on: panic edges. See §13 for resolution, nesting, and blob semantics.

7. Edges

FieldTypeDescription
from / tostringRequired. Source and target node ids.
labelstringConnects the edge to an exclusive-gateway branch (branches[].edge).
onstringAlternative trigger. Absent → normal flow. "error" → followed when the source node fails definitively (retries exhausted). "panic" → followed when the source's task panics (an extension bug).
{ "from": "create", "to": "next" },                       // normal flow
{ "from": "create", "to": "compensate", "on": "error" },  // failure route
{ "from": "create", "to": "quarantine", "on": "panic" }   // bug route

Build-time rules: on: edges may only leave nodes that execute tasks — task, foreach, subworkflow (ERROR_EDGE_INVALID_SOURCE) — and may not point at a join (ERROR_EDGE_TO_JOIN).

8. Conditions

Conditions are the mini-DSL used by exclusive-gateway branches. A condition is either a comparison or a logical composition:

{ "and": [
    { "path": "$.nodes.fetch.output.status", "eq": 200 },
    { "or": [
        { "path": "$.trigger.priority", "in": ["high", "urgent"] },
        { "not": { "path": "$.trigger.retry_count", "gt": 3 } }
    ]}
]}

A comparison is always { "path": "<JSONPath>", "<operator>": <operand> } — exactly one operator key next to path.

The 13 built-in operators

OperatorOperandTrue when…
eqanyresolved value strictly equals the operand
neanyresolved value differs from the operand (an absent path yields false, not true)
gt / gte / lt / ltenumber or stringordered comparison — numbers with numbers, strings with strings
inarrayresolved value is one of the listed values
containsanyresolved array contains the operand, or resolved string contains the operand substring
existsbooleanthe path resolves (true) / does not resolve (false)
is_nullbooleanthe resolved value is null (true) / is not (false)
starts_with / ends_withstringresolved string has the prefix / suffix
matchesstring (regex)resolved string matches the regular expression (INVALID_REGEX if it does not compile)
Absence semantics. A path that does not resolve is not an error in a condition: exists answers honestly and every other built-in operator yields false. Conditions only fail on definition errors — invalid JSONPath, invalid regex, or an unregistered custom operator.

Custom operators

Any operator key outside the 13 above is treated as a custom operator and resolved against the host's operator registry at evaluation time. If your platform registered between, this just works:

{ "path": "$.trigger.amount", "between": [100, 500] }

Using an unregistered operator fails at build time (UNKNOWN_CONDITION_OPERATOR) — typos never reach runtime. Hosts register operators with expr::operators::global().register(...); see the Infrastructure Manual.

9. Failure Handling

Every failure carries a structured WorkflowError — { "code": "TASK_TIMEOUT", "message": "...", "source_task": "create" }. The full code catalog is in §17. A task node failure goes through this ladder:

  1. Attempt fails (task error, schema violation, or TASK_TIMEOUT).
  2. Retry policy — if attempts remain, wait per the backoff strategy and retry. Each retry receives the same resolved input.
  3. Definitive failure — retries exhausted. If the node has an on: "error" edge, the error is published to $.nodes.<id>.error and execution continues along that edge (the node's report status is error_routed).
  4. No error edge — the whole run fails with that error.

Panics are different

A panic inside a task is a bug in the extension, not a transient condition. The engine isolates it (catch_unwind — your process survives), but it does not retry and does not follow on: error edges. The only route is an explicit on: "panic" edge; otherwise the run fails with TASK_PANIC.

Consuming an upstream error

{ "id": "alert", "kind": "task", "task": "util.log",
  "input": { "level": "error",
             "message": "$.nodes.create.error" } }
// reached via: { "from": "create", "to": "alert", "on": "error" }

10. Task Profiles

A profile is a named, reusable instance of a base task with configuration baked in and its own schemas. Profiles let workflow authors expose a clean domain-specific contract ("acme.create_order" taking {sku, qty}) on top of a generic task (http.request). Once registered, a profile is indistinguishable from any other task — usable in task and foreach nodes alike.

Declare profiles in the document's tasks section (local to the document), or register them programmatically on the registry (shared):

"tasks": [
  {
    "id": "acme.create_order",
    "extends": "http.request",
    "description": "Creates an order in the ACME API",
    "input_schema": {
      "type": "object", "required": ["sku", "qty"],
      "properties": { "sku": { "type": "string" },
                      "qty": { "type": "integer", "minimum": 1 } }
    },
    "output_schema": { "type": "object", "required": ["order_id"] },
    "bind": {
      "url": "https://api.acme.com/orders",
      "method": "POST",
      "auth": { "type": "bearer", "token": { "$secret": "ACME_TOKEN" } },
      "fail_on_error_status": true,
      "body": "@"
    },
    "output": "@.body"
  }
]
FieldDescription
idRequired. Namespaced id the profile registers under. Conflicts fail the build (PROFILE_ID_CONFLICT).
extendsRequired. Id of the registered base task (PROFILE_BASE_NOT_FOUND if absent).
input_schema / output_schemaThe profile's own contract, validated around every invocation.
bindA shape that builds the base task's input from the profile's input: "@" is the entire profile input, "@.path" a sub-path, everything else literal. Omitted → input passes through unchanged. If the bound input violates the base task's schema, the error is PROFILE_BIND_INVALID.
outputOptional shape applied to the base task's output (e.g. "@.body" to unwrap an HTTP response).
Shapes (@.) vs mappings ($.). Mappings resolve against the global execution context. Shapes resolve against a local document: the profile's input (for bind), the base output (for output), or the source/element (for data.transform / data.map). In a shape, a missing path yields null instead of an error.

Inline profiles are scoped: they exist only while their document executes and never leak into the shared registry, so two workflows can define different acme.create_order profiles without conflict.

11. Secrets ($secret)

Credentials never belong in a workflow document — documents get versioned, shared, and logged. Wherever a secret is needed inside a profile's bind, write a reference instead:

"auth": { "type": "bearer", "token": { "$secret": "ACME_TOKEN" } }

References are resolved when the profile is registered, through the host's SecretProvider. The default provider reads environment variables; hosts can plug a vault or KMS (see §15). An unresolvable secret fails the build with SECRET_NOT_FOUND. The reference must be an object with the single key $secret; objects with additional keys are left untouched.

12. Blobs ($blob)

Large binaries travel by reference, never inline in the context JSON:

{ "$blob": "0197a3f1-7c2e-...", "name": "sales.csv", "size": 52428800 }
  • Tasks that produce files return a blob reference — http.request with response_body: "blob", tabular.write, sftp.get.
  • Tasks that consume files accept one — http.request (body_blob, multipart parts), tabular.parse, sftp.put.
  • Pass references between nodes through ordinary mappings: "file": "$.nodes.download.output.body".
  • Transfers are streamed: a 2 GB file moves between an HTTP download and an SFTP upload without ever being loaded into memory.

Lifecycle: the blob store is created per execution and destroyed when the root execution finishes — success or failure. Subworkflows share the parent's store, so blob references can cross the subworkflow boundary in both directions. Blob ids are engine-generated; forged ids are rejected (INVALID_BLOB_ID), and a reference from another execution yields BLOB_NOT_FOUND.

13. Subworkflows

A subworkflow node runs another workflow as if it were a task. Two sources, in precedence order:

  1. Inline — the document's workflows section (names must be unique: SUBWORKFLOW_DUPLICATE_NAME).
  2. Shared registry — a WorkflowRegistry injected at build (§15).

Everything is resolved and validated when the parent executor is built: a missing name (SUBWORKFLOW_NOT_FOUND), a self-referencing chain (SUBWORKFLOW_CYCLE), nesting deeper than 8 levels (SUBWORKFLOW_DEPTH_EXCEEDED), or an invalid child document all fail the parent's build — never the run.

Semantics at runtime:

  • The node's resolved input (or the predecessor's output) becomes the child's $.trigger.
  • The child has its own execution id and its own state document; it cannot read the parent's context.
  • The child shares the parent's blob store and event sequence (observability events of the whole tree share one total order; child events carry parent_execution_id).
  • The child's final output is the node's output. Child failure → on: error; child panic → on: panic.

Reshapes one object with a @. shape template.

data.map

Applies a shape to every element of an array. items (required, array) + shape (required, resolved per element where @ = the element). Output is the transformed array. The canonical companion of foreach.

data.merge

data.template

nameBlob filename (default out.csv / out.xlsx).
headersExplicit column order (default: keys of the first object row).
delimiter / sheetAs in tabular.parse.

Output: { "file": { "$blob": ... } } — chain it into http.request multipart or sftp.put.

sftp — remote file transfer

All three tasks share the connection object:

"connection": {
  "host": "sftp.partner.com", "port": 22, "username": "acme",
  "auth": { "type": "password", "password": { "$secret": "SFTP_PASS" } },
  // or:  { "type": "key", "private_key": "/path/to/id_ed25519", "passphrase": "..." }
  "known_hosts": "/etc/ssh/known_hosts"   // optional but recommended
}

When known_hosts is provided, the server's host key is verified: unknown host → SFTP_HOST_UNKNOWN; mismatched key (possible MITM) → SFTP_HOST_KEY_MISMATCH.

TaskInput (besides connection)Output
sftp.getpath (remote file), name (blob name, default: remote filename){ "file": { "$blob": ... } } — streamed, never buffered in memory
sftp.putfile ($blob ref), path (remote destination){ "path": "...", "size": bytes }
sftp.listpath (remote directory){ "entries": [ { "name", "kind": "file"|"dir"|"other", "size", "modified" } ] }

Common errors: SFTP_ERROR, SFTP_INPUT_INVALID, BLOB_IO_ERROR.

15. Embedding the Engine

Registry setup

// All feature-enabled extensions, pre-registered:
let registry = workflow_forge::default_registry();

// Or build your own and add custom tasks:
let registry = Arc::new(TaskRegistry::new());
workflow_forge::register_extensions(&registry);
registry.register(MyCustomTask::new());   // your own Task implementation

The builder — full dependency injection

WorkflowExecutor::new(workflow, registry) covers the simple case (env-var secrets, temp-dir blobs, no observer). For everything else, use the builder:

let executor = WorkflowExecutor::builder(workflow, registry)
    .secrets(&my_vault)                 // SecretProvider for {"$secret": "X"} (default: env vars)
    .workflows(shared_workflows)        // WorkflowRegistry of shared subworkflows
    .blobs(Arc::new(MyBlobFactory))     // BlobStoreFactory (default: temp dir per execution)
    .observer(history.clone())          // ExecutionObserver for events
    .rule(NoProductionUrlsRule)         // extra ValidationRule(s), run after the built-ins
    .build()?;                          // Err(Vec<WorkflowError>) with every problem found

let result = executor.run(WorkflowData(json!({ ... }))).await;
Builder methodInjectsDefault
.secrets(&dyn SecretProvider)Resolution of $secret references in inline profilesEnvironment variables
.workflows(Arc<WorkflowRegistry>)Shared subworkflows, resolvable by namenone
.blobs(Arc<dyn BlobStoreFactory>)Blob storage backend, one store per executionTemp directory
.observer(Arc<dyn ExecutionObserver>)Receiver of execution events (incl. subworkflows)none
.rule(impl ValidationRule)Host validation rules, also applied to every subworkflowbuilt-ins only

An executor is reusable and thread-safe: build once, call run() many times concurrently. Each run() creates a fresh execution (id, state document, blob store) and runs to completion. Execution is ephemeral in v1 — there is no persistence or resumption; observability events are designed to become a durable journal in future versions.

16. Observability

Register an observer to receive every execution event, in emission order:

let history = Arc::new(InMemoryHistory::new());
let executor = executor.with_observer(history.clone());

executor.run(trigger).await?;

let report = history.report();         // ExecutionReport: status + per-node timeline
let events = history.events();         // raw events, ordered by seq
let executions = history.executions(); // root + subworkflow execution ids

Every event carries execution_id, parent_execution_id (for subworkflows), seq (a total order across the whole execution tree, including parallel branches), elapsed_ms, and a type-discriminated payload:

typeEmitted when
workflow_startedAn execution (root or subworkflow) begins; carries the workflow metadata and trigger.
node_startedA node begins (joins emit it on completion of all branches).
task_attempt_startedA task attempt begins; the resolved input rides along on the first attempt.
task_attempt_failedAn attempt failed; includes will_retry and next_delay_ms.
node_completedA node finished and published its output (with duration_ms).
node_failedA node failed definitively; error_routed tells whether an on: error edge continued the flow.
foreach_item_completed / foreach_item_failedPer-element outcomes of a foreach.
workflow_completed / workflow_failedTerminal events with the final output / error and total duration.

Events serialize to stable JSON — safe to persist. InMemoryHistory is the built-in observer; production hosts typically implement ExecutionObserver to forward events to a database or OTLP pipeline. Observers must not block: on_event is called synchronously from the executor — buffer through a channel if persistence is slow.

ExecutionReport (from history.report()) summarizes a single execution: overall status (running / completed / failed), and per node: status (running / completed / failed / error_routed), attempts, duration, output or error. Use report_for(execution_id) for subworkflow detail.

18.1 Multi-service health monitor — parallel, join, exclusive routing

{
  "spec": "1.0", "name": "health-monitor", "version": "1.0.0",
  "nodes": [
    { "id": "start", "kind": "start" },
    { "id": "fan", "kind": "gateway", "gateway": "parallel" },
    { "id": "check_api",  "kind": "task", "task": "http.request",
      "input": { "url": "$.trigger.api_url" },  "timeout_ms": 5000 },
    { "id": "check_cdn",  "kind": "task", "task": "http.request",
      "input": { "url": "$.trigger.cdn_url" },  "timeout_ms": 5000 },
    { "id": "check_auth", "kind": "task", "task": "http.request",
      "input": { "url": "$.trigger.auth_url" }, "timeout_ms": 5000 },
    { "id": "join", "kind": "gateway", "gateway": "join" },
    { "id": "verdict", "kind": "gateway", "gateway": "exclusive",
      "branches": [
        { "when": { "and": [
            { "path": "$.nodes.check_api.output.status",  "eq": 200 },
            { "path": "$.nodes.check_cdn.output.status",  "eq": 200 },
            { "path": "$.nodes.check_auth.output.status", "eq": 200 }
          ]}, "edge": "healthy" },
        { "else": true, "edge": "degraded" }
      ] },
    { "id": "report", "kind": "task", "task": "data.template",
      "input": { "template": "All systems operational (api={api}, cdn={cdn}, auth={auth})",
                 "values": { "api": "$.nodes.check_api.output.status",
                             "cdn": "$.nodes.check_cdn.output.status",
                             "auth": "$.nodes.check_auth.output.status" } } },
    { "id": "alert", "kind": "task", "task": "data.template",
      "input": { "template": "DEGRADED: api={api}, cdn={cdn}, auth={auth}",
                 "values": { "api": "$.nodes.check_api.output.status",
                             "cdn": "$.nodes.check_cdn.output.status",
                             "auth": "$.nodes.check_auth.output.status" } } },
    { "id": "end", "kind": "end" }
  ],
  "edges": [
    { "from": "start", "to": "fan" },
    { "from": "fan", "to": "check_api" },
    { "from": "fan", "to": "check_cdn" },
    { "from": "fan", "to": "check_auth" },
    { "from": "check_api",  "to": "join" },
    { "from": "check_cdn",  "to": "join" },
    { "from": "check_auth", "to": "join" },
    { "from": "join", "to": "verdict" },
    { "from": "verdict", "label": "healthy",  "to": "report" },
    { "from": "verdict", "label": "degraded", "to": "alert" },

    { "from": "alert",  "to": "end" }
