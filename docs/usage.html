Usage & Implementation Guide

How to write declarative workflows as JSON, embed the engine in a Rust application, and author your own tasks. For the engine's internals and extension seams, see the Core & Architecture manual.

1. Mental model

A workflow is a JSON document describing a directed acyclic graph of nodes wired by edges. You store it, diff it, validate it against the published JSON Schemas — even without the engine — and execute it by embedding the async core in your Rust app. There is no DSL and no macros: the workflow is data.

At runtime each execution owns a single context document. Every node reads its input from that document via JSONPath mappings and publishes its output back into it. Control flow is explicit: gateways branch, fan out and join; tasks do the work; foreach iterates; subworkflows compose.

v1 execution model. Execution is ephemeral and run-to-completion, entirely in memory. There is no persistence, scheduling or external waiting in v1 — the engine is a library your host drives, not a server.

2. Quickstart

Add the facade crate with the feature flags you need:

[dependencies]
workflow-forge = "0.1"   # default features: util, data, http (+ tabular, sftp, or full)
tokio = { version = "1", features = ["full"] }

Parse a workflow, build an executor with the default task registry, and run it:

use workflow_forge::prelude::*;

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let workflow: WorkflowDefinition = serde_json::from_str(r#"{
        "spec": "1.0",
        "name": "greet",
        "version": "0.1.0",
        "nodes": [
            { "id": "start",  "kind": "start" },
            { "id": "render", "kind": "task", "task": "data.template",
              "input": { "template": "Hello {who}!", "values": "$.trigger" } },
            { "id": "end",    "kind": "end" }
        ],
        "edges": [
            { "from": "start",  "to": "render" },
            { "from": "render", "to": "end" }
        ]
    }"#)?;

    let registry = workflow_forge::default_registry();
    let executor = WorkflowExecutor::new(workflow, registry)
        .map_err(|errors| format!("invalid workflow: {errors:?}"))?;

    let result = executor
        .run(WorkflowData(serde_json::json!({ "who": "world" })))
        .await?;

    println!("{}", result.0); // "Hello world!"
    Ok(())
}

WorkflowExecutor::new validates the document and compiles its schemas eagerly — an invalid workflow fails to build, never mid-run. The returned Err is a Vec<WorkflowError> accumulating every problem at once.

Or from the command line

The forge CLI (crate workflow-forge-cli) runs, validates and inspects workflows with all bundled extensions — no Rust required:

forge run workflow.json --input '{"who":"world"}'   # trigger inline…
echo '{"who":"world"}' | forge run workflow.json     # …or piped via stdin
forge run workflow.json --timeout-ms 30000           # opt-in execution deadline
forge validate workflow.json                         # structure + schemas, no run
forge catalog                                        # the task catalog as JSON

3. Workflow document anatomy

The root object:

Field Required Meaning
specdefaults to "1.0"Contract version. Only "1.0" is accepted by this core.
nameyesHuman-readable name, shown in errors and metadata.
versionyesYour workflow's semantic version (free string).
idoptionalStable identifier, if you track workflows by id.
nodesyesThe graph's nodes (exactly one start, ≥1 end).
edgesyesDirected edges connecting node ids.
tasksoptionalInline task profiles local to this document.
workflowsoptionalInline child workflows for subworkflow nodes (precede the shared registry).

4. The context document

Every execution carries one state document. Mappings and conditions read from these roots:

$.trigger              → the initial input of the execution
$.nodes.<id>.output    → the output published by each executed node
$.nodes.<id>.error     → the error of a node, when routed via on: "error"
$.workflow             → metadata (id, name, version, execution_id)

A task node with no input receives the output of its predecessor (the "carried token") directly. Otherwise its input is a mapping resolved against the document above.

5. Mappings ($.)

A node's input (and foreach.items, subworkflow.input) is a JSON value where strings are interpreted as follows:

  • "$.trigger.url" → resolved as JSONPath against the context document.
  • "hello", 42, true, nested objects/arrays → literals. Strings inside nested objects are resolved too if they start with $.
  • "$$.not.a.path" → escape: produces the literal string "$.not.a.path".
  • Paths are singular: the first match is taken; wildcards are not supported in mappings.
  • A mapping path that does not resolve is an error (MAPPING_PATH_NOT_FOUND) — in an input it is almost always a definition bug. (Contrast with conditions, where a missing path is simply false.)
No transform helpers in mappings. Concatenating, formatting or applying defaults is not done inline. Prepare optional or computed values with a data.* node first. There is exactly one place where data is reshaped — a deliberate design choice.

6. Node reference

start

The single entry point; receives the trigger. Optional fields:

  • schema — JSON Schema validating the trigger (fails with SCHEMA_VALIDATION_FAILED).
  • defaults — constants merged into the trigger before execution.

end

A terminal node. A workflow may have several. Fields:

  • status — success (default), error, cancelled, or a custom string.
  • output — optional shape applied to the predecessor's output; otherwise the predecessor output is final.
  • schema — validates the final result (OUTPUT_SCHEMA_VALIDATION_FAILED).

If several end nodes are reached the workflow output is an object keyed by end-node id; with one, it is that node's value.

task

Invokes a registered task. Fields: task (id, e.g. "http.request"), input (mapping), retry, timeout_ms.

{
  "id": "fetch", "kind": "task", "task": "http.request",
  "input": { "url": "$.trigger.url", "fail_on_error_status": true },
  "retry": { "max": 3, "backoff": "exponential", "initial_ms": 500 },
  "timeout_ms": 10000
}

retry = { max, backoff, initial_ms }; backoff is exponential (default), linear or fixed. timeout_ms applies per attempt.

gateway

Control flow, in three kinds:

  • exclusive — if/else. Has branches; each branch is { when: <condition>, edge: "label" } or { else: true, edge: "label" }. Branches are evaluated in order; the first match wins, otherwise the else branch. No match and no else → NO_BRANCH_MATCHED.
  • parallel — fan-out. No branches; all outgoing edges run concurrently. Requires ≥2 outgoing edges.
  • join — fan-in (wait_all). Waits for every normal incoming branch; its output is an object { "<source_node>": output, … }. Requires ≥2 normal incoming edges.
{
  "id": "check", "kind": "gateway", "gateway": "exclusive",
  "branches": [
    { "when": { "path": "$.nodes.fetch.output.status", "eq": 200 }, "edge": "ok" },
    { "else": true, "edge": "fail" }
  ]
}

foreach

Invokes a task once per array element — the complement of data.map (which only reshapes).

{
  "id": "create_orders", "kind": "foreach",
  "items": "$.nodes.adapt.output",   // must resolve to an array
  "task": "acme.create_shipment",
  "concurrency": 5,                   // default 1 (sequential)
  "throttle_ms": 200,                 // min spacing between item starts
  "on_item_error": "collect",         // "fail" (default) | "collect"
  "retry": { "max": 2 }, "timeout_ms": 10000
}
  • Each element is the direct input of the task; reshape per element with data.map first.
  • concurrency limits in-flight items; throttle_ms spaces out item starts (rate limit toward the target).
  • on_item_error: "fail" — first error cancels in-flight items and the node fails (its on: error edges apply). Output: array of outputs in items order.
  • on_item_error: "collect" — all run; output { "ok": [...], "failed": [{ index, item, error }] } and the node does not fail. (A panic still aborts the whole node.)

subworkflow

Runs another workflow as if it were a task — the reuse block above profiles.

{
  "id": "process", "kind": "subworkflow", "workflow": "normalize-and-send",
  "input": { "date": "$.trigger.order_date", "total": "$.trigger.amount" }
}

The resolved input (or the predecessor token) becomes the child's trigger; the child's final output is the node's output. The child is resolved by name — inline workflows first, then the shared registry — and everything (existence, cycles, depth ≤ 8) is checked at build time. Error and panic in the child route through the node's on: error / on: panic edges. The child shares the root's blob store.

7. Condition mini-DSL

Conditions (used in exclusive gateway branches) are JSON too — a comparator over a path, or a logical composition:

{
  "and": [
    { "path": "$.nodes.fetch.output.status", "eq": 200 },
    { "or": [
      { "path": "$.trigger.priority", "in": ["high", "urgent"] },
      { "path": "$.trigger.retry_count", "gt": 3 }
    ]}
  ]
}
GroupOperators
Comparisoneq ne gt gte lt lte
Membershipin contains
Existence / typeexists is_null
Stringsstarts_with ends_with matches (regex)
Logicaland or not

A path that does not resolve is not an error in a condition: exists yields false and comparators yield false — a workflow never crashes because a condition path is absent. Hosts can register extra operators (see the architecture manual).

8. Edges & error routing

{ "from": "check", "label": "ok", "to": "notify" }   // gateway branch
{ "from": "fetch", "on": "error", "to": "alert" }    // operational failure
{ "from": "fetch", "on": "panic", "to": "cleanup" }  // bug in the task

Every task-running node has three routable outputs:

  • success (default edge, or labelled for gateways).
  • on: "error" — taken when the node exhausts its retries.
  • on: "panic" — taken when the task panics. A panic never retries (a bug is not transient) and never falls back to on: error (it may have left half-finished effects). Without a panic edge, the workflow fails.

Trigger edges (on: error/on: panic) may only leave task/foreach/subworkflow nodes and may not enter a join gateway.

9. Task profiles

A profile is a named, reusable instance of a registered task with configuration baked in — a concrete client endpoint promoted to a first-class task.

{
  "id": "acme.create_order",
  "extends": "http.request",
  "description": "Create an order in Acme",
  "input_schema":  { "type": "object", "required": ["sku", "qty"] },
  "output_schema": { "type": "object", "required": ["order_id"] },
  "bind": {
    "url": "https://api.acme.com/orders",
    "method": "POST",
    "auth": { "type": "bearer", "token": { "$secret": "ACME_TOKEN" } },
    "fail_on_error_status": true,
    "body": "@"
  },
  "output": "@.body"
}
  • extends — an already-registered task (or another profile; chains are allowed, cycles impossible).
  • bind — a shape that builds the base task's input from the profile's input. @ is the whole input, @.path a subpath (missing → null), @@. escapes, the rest are literals. Without bind, the input passes through.
  • output — optional shape over the base output (e.g. "@.body"), validated against output_schema.
  • Secrets — {"$secret":"NAME"} in bind are resolved when the profile is registered, so versioned definitions carry no credentials.

Register profiles either via TaskRegistry::register_profile() (shared) or the tasks section of the document (local to that workflow). A registered profile is just another task: it appears in the catalog and the engine validates its input/output like any other.

The resulting integration pattern: trigger (client JSON) → a data.transform node that reshapes it field by field → a preconfigured profile that performs the call. Every piece is declarative, validatable and reusable.

10. Blobs & secrets

The context is JSON; large files never travel inline. A task that produces a file returns a blob reference:

{ "file": { "$blob": "01J…", "name": "sales.csv.gz", "size": 52428800 } }

Blobs are backed by a per-execution store (v1: a temp directory cleaned up when the run ends) and streamed, never base64-inlined. Tasks like tabular.*, sftp.* and http.request (with response_body: "blob" or body_blob) exchange these references.

Secrets use the {"$secret":"NAME"} convention inside a profile's bind, resolved at registration through a SecretProvider (default: environment variables).

11. Authoring your own tasks

A task is the unit of extension. There are three levels of effort — pick the lowest that fits.

Level 1 — typed closure (recommended)

Write two Rust types; the engine derives their JSON Schemas via schemars. Input/output validation and the catalog entry come for free.

use serde::{Deserialize, Serialize};
use schemars::JsonSchema;

#[derive(Deserialize, JsonSchema)]
struct CreateShipmentIn { sku: String, qty: u32 }

#[derive(Serialize, JsonSchema)]
struct CreateShipmentOut { tracking: String }

registry.register_typed("acme.create_shipment", |ctx, input: CreateShipmentIn| async move {
    // ctx exposes per-execution resources: ctx.blobs(), ctx.execution_id()
    Ok(CreateShipmentOut { tracking: format!("{}-{}", input.sku, input.qty) })
});

Level 2 — raw closure

For trivial JSON-in/JSON-out tasks, skip the types entirely (no schema):

registry.register_fn("util.echo", |_ctx, input| async move { Ok(input) });

Level 3 — the Task trait

When a task needs to hold state or dependencies (a DB pool, a configured HTTP client) or read the full execution state, implement the trait directly — the struct you register can carry whatever it needs.

use workflow_forge::prelude::*;
use async_trait::async_trait;

struct MyTask { manifest: TaskManifest /* + pools, clients, config… */ }

#[async_trait]
impl Task for MyTask {
    fn manifest(&self) -> &TaskManifest { &self.manifest }
    async fn execute(&self, ctx: &WorkflowContext, input: WorkflowData) -> WorkflowResult {
        Ok(input) // your logic here
    }
}

Validation: tolerant by default, strict on request. For typed tasks the engine validates input against the derived schema before the closure runs and output after; nested types and enums are fully enforced. By default extra/undeclared input fields are accepted (forward-compatible). To reject unknown fields, add #[serde(deny_unknown_fields)] — schemars honors it (emits additionalProperties: false), keeping schema and deserialization aligned.

12. Official extensions

Enable via feature flags on the workflow-forge facade (util, data, http on by default; add tabular, sftp, or full).

util

TaskContract
util.noopReturns its input unchanged.
util.log{ message, level?, value? } → logs and returns value (or null).
util.delay{ ms, value? } → sleeps, then returns value (or null).

data — all reshaping lives here

TaskContract
data.transform{ source, shape } — apply a shape (@.path relative to source; missing → null) to one object.
data.map{ items, shape } — apply the shape to each array element.
data.merge{ objects: [...] } — deep merge in order; later keys win; arrays/scalars replaced whole.
data.template{ template, values } — interpolate {path.with.dots}; {{/}} escape; output string.
data.cast{ source, fields, on_invalid? } — per-field conversions: date/number/int/bool/string/trim/upper/lower/replace/default; on_invalid: fail/null/collect.

http

http.request — methods, headers, query, basic/bearer auth. A 4xx/5xx is not an error by default (status is data; route it with a gateway); set fail_on_error_status: true to make it fail and trigger retry/on: error.

  • Request body (mutually exclusive): body (JSON), form (urlencoded), text (raw), body_blob (binary, streamed from a $blob), multipart (form-data; parts may be text/json/blob).
  • Response: response_body = auto (JSON if content-type is json, else string), text, or blob (streamed to the BlobStore; body is a $blob reference).
  • Output: { status, headers, body }.

tabular & sftp — via $blob

TaskContract
tabular.parse{ file: $blob, format?, headers?, delimiter?, sheet? } → { rows, count } (CSV / XLSX).
tabular.write{ rows, format, name?, … } → { file: $blob }.
sftp.get{ connection, path, name? } → { file: $blob } (streamed download).
sftp.put{ connection, file: $blob, path } → { path, size } (streamed upload).
sftp.list{ connection, path } → { entries: [{ name, kind, size, modified }] }.
Connection reuse at volume. The default http.request already pools connections (one shared reqwest::Client); inject a tuned client with workflow_forge_ext_http::register_with_client. For SFTP, workflow_forge_ext_sftp::register_pooled(&registry, max_idle) reuses authenticated SSH sessions across calls (keyed by connection, liveness-checked) — register it instead of the default when a foreach hammers the same host.

13. Observability

Register an observer to receive typed events (zero cost when absent). The built-in InMemoryHistory accumulates events and produces a serializable report:

use std::sync::Arc;
use workflow_forge::prelude::*;

let history = Arc::new(InMemoryHistory::new());
let executor = WorkflowExecutor::builder(workflow, registry)
    .observer(history.clone())
    .build()
    .map_err(|e| format!("{e:?}"))?;

executor.run(WorkflowData(trigger)).await?;

let report = history.report();          // root execution: status + per-node timeline
println!("{}", serde_json::to_string_pretty(&report)?);

Events include workflow_started/completed/failed, node_started/completed/failed, task_attempt_started/failed and foreach_item_completed/failed, each carrying execution_id, a total-order seq and elapsed_ms. See the architecture manual for the full event contract.

Dry-run testing with mock tasks

Enable the testing feature to swap a real task (an HTTP call, an SFTP transfer, a client profile) for a MockTask, run the workflow with the real executor, and assert both the output and what it would have called — no network, filesystem or secrets.

use std::sync::Arc;
use workflow_forge::prelude::*;
use workflow_forge::testing::MockTask;   // feature = "testing"

let registry = Arc::new(TaskRegistry::new());
let mock = MockTask::returning("acme.create_order", serde_json::json!({ "order_id": "o-1" }));
let calls = mock.call_log();              // grab the handle BEFORE registering
registry.register(mock);

let executor = WorkflowExecutor::new(workflow, registry).map_err(|e| format!("{e:?}"))?;
let out = executor.run(WorkflowData(trigger)).await?;

assert_eq!(calls.count(), 1);
assert_eq!(calls.nth(0), Some(expected_request));

MockTask::failing(id, err) drives on: "error" routes and retries; MockTask::with_fn(id, |input| …) computes a response from the input.

14. Errors & validation

Every failure is a structured WorkflowError with a stable code, a message and a source_task. Two distinct phases:

  • Build time — graph structure, node/edge references, gateway coherence, reachability, acyclicity, task existence, schema validity, subworkflow cycles/depth, profile/secret resolution. WorkflowExecutor::new returns all of these at once as a Vec<WorkflowError>.
  • Run time — trigger/input/output schema validation, task timeouts and panics, foreach item failures, unmatched exclusive branches, incomplete joins.

The complete catalog of error codes and the rules that emit them is documented in the Core & Architecture manual.
