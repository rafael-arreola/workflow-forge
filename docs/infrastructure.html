Core Architecture & Extensibility

A complete, code-faithful tour of the engine's internals — every module family, the spec types, the validation pipeline, the executor's traversal and policy, the resource and observability subsystems — and the seams designed for future expansion. References point at concrete source locations in crates/core/src/.

1. Philosophy & foundational decisions

Workflow Forge is a declarative, JSON-defined workflow engine in the spirit of BPMN / Step Functions / CNCF Serverless Workflow, but with its own spec, designed to be embedded as a Rust library first. Two contracts are published independently of the code: the workflow schema (what a valid workflow is) and the extension manifest schema (how a task declares its config and I/O). These make a workflow validatable and a catalog generatable without the engine — the foundation for tooling and, eventually, visual editors.

The shape of the core follows directly from a set of deliberate decisions:

DecisionChoice & rationale
Product formEmbeddable library first; CLI / server / durable runtime are later phases on the same core.
StructureExplicit graph (nodes + edges), not a nested tree — directly editable and analyzable.
Execution (v1)Ephemeral, in-memory, run-to-completion. Durability is deferred (events are designed as its seed).
Data flowOne global context document per execution + JSONPath mappings; each node publishes to $.nodes.<id>.output.
BranchingExplicit gateway nodes (exclusive / parallel / join), conditions in the node, labelled edges.
ExtensionsCompile-time Rust traits; the JSON manifest contract is shaped so a WASM loader is "just a new loader" later.
ErrorsPer-node policy (retry, timeout_ms) + optional on: error / on: panic edges; no compensation/sagas in v1.
ConditionsA JSON mini-DSL (validatable by schema, buildable by a UI), not an embedded expression language.
MappingsPure JSONPath + literals; every transform is an explicit data.* node — one place reshapes data.
Binaries$blob convention + a BlobStore trait (temp dir in v1), so large files stream and never inline.
ObservabilityTyped, serializable ExecutionEvents via an observer trait — the future durable journal, frozen now.

2. Workspace & crate layout

crates/
  core/                  workflow-forge-core   — spec types, executor, validation, BlobStore, manifest
  extensions/
    util/ data/ http/ tabular/ sftp/ compress/  — official extensions (one crate each)
  forge/                 workflow-forge        — facade: re-exports core + registers extensions by feature
  cli/                   workflow-forge-cli    — the `forge` binary (run/validate/catalog)

Two rules keep the dependency graph clean:

  • Every extension depends only on core, never on another extension. Each exposes a register(&TaskRegistry) function and ships its own integration tests against the real executor.
  • The workflow-forge facade re-exports the core prelude and, behind feature flags (util, data, http on by default; tabular, sftp; full), wires the official extensions into a ready-made registry via default_registry(). forge/src/lib.rs:53–71

The spec contract is versioned independently from the crates: workflows declare "spec": "1.0", the JSON Schemas live under schemas/<version>/ with stable $ids, and a crate bump never implies a spec bump.

5. The validation pipeline

Validation runs entirely at build time and accumulates every error into a Vec<WorkflowError> — it never stops at the first. validate/mod.rs:46–79 A ValidationCtx builds shared indices once (node map, incoming/outgoing adjacency, start nodes — including broken references so dependent rules can still inspect them). validate/context.rs:13–75

pub trait ValidationRule: Send + Sync {
    fn codes(&self) -> &'static [&'static str];
    fn check(&self, wf: &WorkflowDefinition, ctx: &ValidationCtx, errors: &mut Vec<WorkflowError>);
}

Rules run in a fixed order (rules::BUILTIN), then any host-supplied rules, then recursively into each inline child workflow. validate/rules/mod.rs:18–32

Host rules are injected via WorkflowExecutor::builder(…).rule(Box<dyn ValidationRule>) and run after the built-ins, recursively into child workflows. Task-existence is checked separately (validate_tasks → TASK_NOT_FOUND) and schema validity during compilation (INVALID_SCHEMA).

6. The runtime

6.1 Executor construction runtime/executor.rs

Three entry points — new, new_with_secrets, and builder().build() — all funnel into build_internal executor.rs:185–323, which performs, in order:

  1. Scoped registry — inline tasks profiles are registered into a registry.scoped() copy so the shared registry is never mutated; a failed registration fails the build.
  2. Structural validation — validate_with() (all rules) + validate_tasks() (every referenced task exists).
  3. Schema compilation — CompiledSchemas::build() precompiles every JSON Schema (start trigger, end result, and each referenced task's input/output) into jsonschema::Validators once, not per attempt.
  4. Graph indexing — GraphIndex::build() precomputes adjacency and edge classes.
  5. Subworkflow resolution — each subworkflow node is resolved (inline workflows first, then the shared WorkflowRegistry) and its child executor built recursively; an ancestry stack detects cycles (SUBWORKFLOW_CYCLE) and enforces MAX_SUBWORKFLOW_DEPTH = 8 (SUBWORKFLOW_DEPTH_EXCEEDED); a missing child is SUBWORKFLOW_NOT_FOUND.
  6. Observer propagation — the same observer is set recursively on all child executors.

The resulting WorkflowExecutor holds: workflow, scoped registry: Arc<TaskRegistry>, index: GraphIndex, schemas: CompiledSchemas, optional observer, blobs: Arc<dyn BlobStoreFactory>, and subworkflows: HashMap<NodeId, WorkflowExecutor>. Everything that can be validated or resolved is settled here; runtime only validates data (trigger/input/output against schemas).

6.2 Graph index runtime/graph.rs:7–95

Edges are classified once into three maps plus an in-degree count:

struct GraphIndex {
    nodes: HashMap<NodeId, Node>,
    outgoing:       HashMap<NodeId, Vec<FlowEdge>>,  // normal flow (no on:)
    outgoing_error: HashMap<NodeId, Vec<FlowEdge>>,  // on: error
    outgoing_panic: HashMap<NodeId, Vec<FlowEdge>>,  // on: panic
    incoming_count: HashMap<NodeId, usize>,          // normal-flow in-degree (join arity)
    start: NodeId,
}

Only normal-flow edges count toward a join's expected arity; error/panic routes are tracked separately. Exclusive-gateway label matching filters outgoing by label at run time.

6.3 Traversal executor.rs:352–626

run() creates a WorkflowContext, emits WorkflowStarted, and walks the graph by recursive-descent async from the start node (execute_from), threading a RunState:

struct RunState {
    joins: Mutex<HashMap<NodeId, JoinArrivals>>,  // accumulating fan-in arrivals
    ends:  Mutex<Vec<(NodeId, Value)>>,           // collected terminal results
}
  • continue_through drives a node's outgoing edges: a single edge runs sequentially; multiple edges (a parallel gateway's fan-out) run concurrently via futures::future::try_join_all — the first error short-circuits and sibling futures are dropped (cancellation by drop).
  • Join arrivals are appended under a mutex; when arrivals.len() == incoming_count, the entry is removed and the join continues, emitting its events and an output object { source_node: output, … }. Earlier arrivals simply terminate their branch.
  • Output aggregation: 0 ends reached → NO_OUTPUT; 1 end → that value; N ends → an object keyed by end-node id. A join still waiting at the end (a branch died on an unhandled error) is detected as JOIN_INCOMPLETE.

6.4 Execution policy runtime/policy.rs:24–175

Tasks and foreach items share execute_with_policy:

  1. Validate input against the precompiled schema → TASK_INPUT_INVALID.
  2. Attempt loop (1-indexed). Each attempt wraps the task future in AssertUnwindSafe(…).catch_unwind() and, if set, tokio::time::timeout(timeout_ms). A timeout is TASK_TIMEOUT; a caught panic becomes TASK_PANIC via panic_error (downcasts the payload to a message).
  3. On success, validate output → TASK_OUTPUT_INVALID, then return.
  4. On error, decide retry: a TASK_PANIC never retries; otherwise retry while attempt ≤ retry.max. The delay comes from backoff_delay: Exponential = initial·2^(n-1), Linear = initial·n, Fixed = initial, all saturating. A TaskAttemptFailed event carries will_retry and next_delay_ms; then tokio::time::sleep(delay) and loop.

7. The context document runtime/context.rs

A WorkflowContext owns the per-execution state document behind an RwLock, so concurrent parallel branches read and write safely.

struct WorkflowContext {
    execution_id: String,                 // UUID v7
    parent_execution_id: Option<String>,  // set for sub-workflows
    started_at: Instant,
    state: RwLock<Value>,                  // { trigger, nodes, workflow }
    blobs: Arc<dyn BlobStore>,             // shared with children
    event_seq: Arc<AtomicU64>,             // total event order across the tree
}

Key methods: with_state(f) (read under lock, no clone), snapshot(), set_node_output / set_node_error (publish to $.nodes.<id>), blobs(), next_event_seq(). A child context (child_of) gets its own state document and execution_id but shares the parent's blobs and event_seq — so $blob references cross the boundary (the root cleans up) and events keep a single total order across the whole tree.

8. Expressions (expr)

Three resolution conventions, all on top of a shared JSONPath helper.

ConventionResolves againstUnresolvedModule
$.path (mapping)the full execution contexterror MAPPING_PATH_NOT_FOUNDexpr/mapping.rs
@.path (shape)a local source valuenull (no error)expr/shape.rs
condition paththe full execution contextfalse (no error)expr/operators.rs
  • mapping — resolve(mapping, context): strings starting with $. are JSONPath (singular: first match, no wildcards), $$. escapes to a literal $., objects/arrays recurse, everything else is literal.
  • path — query_first(doc, path) wraps jsonpath-rust and returns only the first match; a malformed path is INVALID_JSONPATH. A process-global OnceLock<RwLock<HashMap>> caches compiled regexes (used by matches) across runs.
  • operators — the ConditionOperator trait (key() + evaluate(Option<&Value>, &Value)) backs both built-ins and host extensions. A process-global OperatorRegistry (operators::global()) holds them; built-ins return false on an unresolved path; custom operators receive None and decide their own semantics.
  • shape — apply_shape(shape, source): @ is the whole source, @.path a JSONPath relative to it (missing → null), @@. escapes. Shared by data.transform and profile bind/output.

9. Resources (io)

Blobs io/blob.rs

A BlobRef serializes with the $blob key ({ "$blob": id, name?, size? }). The BlobStore trait is async:

trait BlobStore: Send + Sync {
    async fn put(&self, data: Vec<u8>, name: Option<String>) -> Result<BlobRef, WorkflowError>;
    async fn get(&self, blob: &BlobRef)                  -> Result<Vec<u8>, WorkflowError>;
    async fn import_file(&self, path: &Path, name: Option<String>) -> Result<BlobRef, WorkflowError>;
    async fn local_path(&self, blob: &BlobRef)           -> Result<PathBuf, WorkflowError>;  // for streaming
    async fn cleanup(&self)                              -> Result<(), WorkflowError>;
}
trait BlobStoreFactory: Send + Sync { fn create(&self, execution_id: &str) -> Arc<dyn BlobStore>; }

The v1 default TempDirBlobStore uses a directory {tmp}/workflow-forge-{execution_id}, ids are UUID v7, and ids are validated against path traversal (alphanumeric + - only → INVALID_BLOB_ID). I/O is async via tokio::fs; a Drop guard cleans up even on panic. Errors: BLOB_NOT_FOUND, BLOB_IO_ERROR. Inject a custom backend (S3, DB, memory) with builder().blobs(factory).

Secrets io/secret.rs

The SecretProvider trait is a single get(&str) -> Option<String>; the default EnvSecrets reads environment variables. resolve_secrets(&mut Value, provider) recursively replaces {"$secret":"NAME"} objects, and is called at profile registration time (so versioned definitions never embed credentials). A missing secret is SECRET_NOT_FOUND. Inject a custom provider (Vault, KMS) via register_profile(..., provider) or the builder's secrets(...).

11. The task family (task)

The contract task/mod.rs

#[async_trait]
trait Task: Send + Sync + 'static {
    fn manifest(&self) -> &TaskManifest;
    async fn execute(&self, ctx: &WorkflowContext, input: WorkflowData) -> WorkflowResult;
    fn task_id(&self) -> &TaskId { &self.manifest().id }  // default
}
struct TaskManifest { id: TaskId, description: Option<String>,
                      input_schema: Option<schemars::Schema>, output_schema: Option<schemars::Schema> }

The manifest is serializable: TaskRegistry::catalog() exports every registered task's manifest as JSON — the contract that powers validation, documentation, and future editors without the engine.

The registry task/registry.rs

An Arc<RwLock<HashMap<TaskId, Arc<dyn Task>>>> — concurrent reads, occasional registration. Methods: register, register_arc, register_typed, register_fn, register_profile, get, list, contains, catalog, and scoped(). scoped() is a shallow copy (shared Arc tasks, cloned map) — the basis for per-document inline profiles that never pollute the shared registry.

Profiles task/profile.rs

A ProfileTask wraps a base Arc<dyn Task> with a resolved bind shape, an optional output shape, and a precompiled validator for the base's input. At execution: apply bind to the profile input → validate against the base's schema (PROFILE_BIND_INVALID) → run the base → apply output. Secrets in bind are resolved once, at registration. Registration errors: PROFILE_BASE_NOT_FOUND, PROFILE_ID_CONFLICT, SECRET_NOT_FOUND.

Typed & closure adapters task/typed.rs

Three escalating levels of authoring ergonomics, all producing a Task:

  1. register_typed → TypedTask<In, Out, F>: a closure over your own types. The manifest's input_schema/output_schema are derived with schemars::schema_for!. execute deserializes In (mismatch → TASK_INPUT_INVALID), runs the closure, serializes Out (failure → TASK_OUTPUT_INVALID). Validation is thus two aligned layers (engine schema + serde), and nested/enum schemas with internal $ref/$defs are fully enforced.
  2. register_fn → FnTask<F>: a closure over raw WorkflowData; no schemas.
  3. impl Task: a full struct that can carry state/dependencies (a DB pool, an HTTP client) and read the full &WorkflowContext.

Both closure adapters receive a TaskCtx — an owned, cheap snapshot of per-execution resources (execution_id, parent_execution_id, blobs). It is passed by value deliberately: it lets the closure's future be 'static and keeps closure type-inference clean, sidestepping the borrow/lifetime issues of handing out &WorkflowContext.

Tolerance. Derived schemas are tolerant by default — schemars does not emit additionalProperties: false and serde ignores unknown fields, so extra input keys pass. Adding #[serde(deny_unknown_fields)] flips both layers to strict in lockstep, because schemars reads the same serde attributes the deserializer uses.

12. Error model & catalog error/*

WorkflowError is the single error type — it travels serialized between nodes (on: error routes), inside events, and as validation output.

struct WorkflowError {
    code: String,                  // stable identifier from error::codes
    message: String,
    source_task: Option<String>,   // originating task/node
    payload: Option<Box<WorkflowData>>,  // offending input

13. Extending the core

The core is extensible without modification through a handful of seams. The lib.rs "where do I add…?" table core/src/lib.rs:23–36 is the canonical map; the seams in detail:

To add…Do thisSpec change?
a task (fast)register_typed (typed, derived schemas) or register_fn (raw JSON)no
a task (stateful)implement Task on a struct holding your dependencies; register itno
a task profileTaskProfile + register_profile (or inline tasks)no
a condition operatorimplement ConditionOperator, register in operators::global() before buildingno
a validation ruleimplement ValidationRule → builder().rule(...)no
a blob backendimplement BlobStore + BlobStoreFactory → builder().blobs(...)no
a secret providerimplement SecretProvider → builder().secrets(...)no
an error codeadd a documented constant in error::codes (+ ALL); values are immutablecontract
an event kindadd a variant to observe::EventKind (+ node_id())contract
a node kindvariant in spec::node::NodeKind + handler in runtime::handlers + rules in validate::rulesyes

A task is the universal extension unit. Because the engine knows no task ahead of time, almost anything you want to do is a new task — so the highest-leverage extension surface is task authoring, which is why three ergonomic tiers exist. Node kinds are a closed enum on purpose: composition (task + foreach + subworkflow) covers the cases, and opening them would break static validation and the published schema.

Writing an official-style extension crate. Create crates/extensions/<name> depending only on core, expose pub fn register(&TaskRegistry) that registers each task with its manifest, ship integration tests against the real executor, and (optionally) wire a feature flag in the facade.

14. Roadmap & frozen contracts

v1 is intentionally an embeddable, ephemeral library. The post-v1 directions were each given a frozen seam now so they require no redesign later:

Future capabilityFrozen seam that makes it additive
WASM extensions (install without recompiling)The serializable TaskManifest is the whole extension contract — a WASM loader consumes the same manifest, so the spec is unchanged. Compile-time traits become "just one more loader".
Durable / event-sourced executionThe typed, totally-ordered ExecutionEvent stream is designed as the journal. A future EventStore persists events and a replay reconstructs state; the event contract is frozen here.
Visual editorThe explicit graph + published workflow/extension schemas + catalog() export already make a builder UI possible.
Pluggable storage backends (S3, …)BlobStoreFactory is the injection point; the temp-dir store is just the default.

The honest boundary: v1 deliberately has no persistence, no external wait-states, no triggers/scheduling and no server. Those belong to a hosting layer above this library, built on the seams above — not to the embeddable core. (Per-run limits are in the core: run_with(trigger, RunOptions) takes an optional total deadline and a cooperative CancellationToken; runs are unlimited by default. The forge CLI is that thin hosting layer in binary form: run/validate/catalog over the same executor and default_registry().)
