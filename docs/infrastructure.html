workflow-forge — Infrastructure Manual

The engineering reference for maintaining, extending and improving the workflow-forge engine. It documents every component of the core, how they work, how they communicate, and exactly where to plug in new behavior. If you only want to use the library, read the User Manual instead.

1. Purpose & Scope

The engine (crates/core, package workflow-forge-core) executes workflow documents conforming to spec 1.0. Its architecture pursues four goals, in this order:

  1. Extensible — every behavior a host might want to change is behind a trait with a registration point; the engine knows no concrete task, storage, or operator in advance.
  2. Curable — responsibilities are closed per module ("family"); a bug in gateway routing can only live in a handful of known files.
  3. Testable — every unit (rule, operator, handler, policy) is testable in isolation; behavior is locked by ~160 tests across the workspace.
  4. Documented — #![warn(missing_docs)] is enforced; every module opens with a //! header stating what it does, how, and why.

3. Core Architecture

The core is organized in eight families with closed responsibilities. The compile pipeline goes top-down; the supporting families serve the pipeline sideways:

          ┌────────────────────────────────────────────────┐
          │  spec      the language: pure serde data types  │
          └───────────────────────┬────────────────────────┘
                                  ▼
          ┌────────────────────────────────────────────────┐
          │  validate  static rules, accumulate all errors  │
          └───────────────────────┬────────────────────────┘
                                  ▼
          ┌────────────────────────────────────────────────┐
          │  runtime   executor · context · handlers · policy │
          └────────────────────────────────────────────────┘

   expr     $. mappings, @. shapes, condition evaluation + operator registry
   task     the extension contract: Task, TaskRegistry, profiles
   io       BlobStore/Factory ($blob) · SecretProvider ($secret)
   observe  ExecutionObserver · ExecutionEvent · InMemoryHistory

Where dependency injection lives

The single DI point of the runtime is WorkflowExecutorBuilder (runtime/executor.rs):

Two more extension surfaces are registries rather than builder arguments: task::TaskRegistry (tasks/profiles) and expr::operators::global() (condition operators, process-wide).

A deliberate non-trait: node kinds. spec::node::NodeKind is a closed enum — the node vocabulary belongs to the spec, not to hosts. Engine extensibility flows through tasks, not through new kinds. The per-kind execution logic is organized as impl WorkflowExecutor blocks in separate files (runtime/handlers/), which gives the same modularity as a NodeHandler trait without dynamic-dispatch ceremony for a vocabulary that cannot grow at runtime. Adding a kind is a spec change with a documented checklist (§6.7).

4. The Families

4.1 spec/ — the language

Pure data, zero logic. Everything here is serde types mirroring the JSON document. If a struct in spec needs behavior beyond (de)serialization and trivial accessors, that behavior belongs in another family.

FileContains
workflow.rsWorkflowDefinition (spec, id, name, version, tasks, workflows, nodes, edges), FlowEdge (from/to/label/on), EdgeTrigger (Error | Panic)
node/mod.rsNodeId, Node (id + flattened kind), NodeKind enum (closed; kind is the JSON tag; name() returns the discriminator string), SubworkflowNode
node/event.rsStartNode (schema, defaults), EndNode (status, output, schema), EndStatus
node/task.rsTaskNode (task, input, retry, timeout_ms), RetryPolicy (max, backoff, initial_ms=500), Backoff (Exponential default | Linear | Fixed)
node/foreach.rsForeachNode (task, items, concurrency=1, throttle_ms, on_item_error, retry, timeout_ms), OnItemError (Fail default | Collect)
node/gateway.rsGatewayNode, GatewayKind (Exclusive | Parallel | Join), Branch (when, is_else as "else", edge)
condition.rsCondition (And/Or/Not/Compare), Comparison (path + op), CompareOp — 13 typed variants + Custom { key, operand }
profile.rsTaskProfile — the declarative profile definition (id, extends, schemas, bind, output). The executable counterpart lives in task::profile.

Hand-written serde, on purpose

Three deserializers are manual, all for the same reason — error quality and open vocabulary:

  • Condition: an untagged derive produces the useless "data did not match any variant"; the manual impl reports exactly which key is missing or extraneous ("expected 'and', 'or', 'not' or a comparison with 'path'; keys found: [foo]").
  • Comparison: enforces "exactly one operator key next to path" with a precise message.
  • CompareOp::from_key_operand: the 13 spec keys are matched and their operand types verified (in wants an array, exists a bool, matches a string…). Any unknown key becomes CompareOp::Custom — this is the deserialization-side half of the extensible operator vocabulary. Serialization round-trips Custom keys verbatim.

4.2 expr/ — expression resolution

FileContains

Every path resolution in the engine funnels through here — change JSONPath behavior in exactly one place.

The operator registry

pub trait ConditionOperator: Send + Sync + 'static {
    fn key(&self) -> &'static str;
    fn evaluate(&self, value: Option<&Value>, operand: &Value)
        -> Result<bool, WorkflowError>;
}

pub fn global() -> &'static OperatorRegistry   // OnceLock, process-wide
  • Condition::evaluate(context) / Comparison::evaluate(context) use the global registry; evaluate_with(context, registry) takes an explicit one (tests, isolated vocabularies).
  • Built-in operator semantics live here as one match over CompareOp; Custom variants are looked up in the registry — an unregistered key is UNKNOWN_CONDITION_OPERATOR at evaluation, but the validation rule catches it at build time first.
  • Absence contract: operators receive value: None when the path did not resolve and decide their own semantics. Built-ins return false (except exists). Operators must only fail on definition errors, never on data.

4.3 validate/ — static rules

Everything detectable before execution is detected here. Validation is a pipeline of rules that share one error vector and accumulate (never stop at the first error — a document gets fixed in one pass).

pub trait ValidationRule: Send + Sync {
    fn codes(&self) -> &'static [&'static str];  // living documentation
    fn check(&self, workflow: &WorkflowDefinition,
             ctx: &ValidationCtx<'_>, errors: &mut Vec<WorkflowError>);
}

pub fn validate(workflow) -> Result<(), Vec<WorkflowError>>          // built-ins
pub fn validate_with(workflow, extra: &[&dyn ValidationRule]) -> …   // + host rules
pub fn validate_tasks(workflow, registry) -> …                       // needs the TaskRegistry
  • ValidationCtx (context.rs) precomputes node lookup, outgoing/incoming edge indexes and start nodes once, shared by all rules.
  • rules::BUILTIN: &[&dyn ValidationRule] fixes the execution order. Host rules run after built-ins and can inspect already-reported errors.
  • validate_with recurses into the document's inline workflows, prefixing child errors with the child's name.
  • codes() is verified by test: every built-in rule's declared codes must exist in error::codes::ALL.

4.4 runtime/ — execution

FileResponsibility
executor.rsOrchestration only: validated construction (build_internal), graph traversal (execute_from dispatching on kind, continue_through following edges, after_task_result applying the error/panic routing ladder), run lifecycle (run → run_with_ctx → blob cleanup at the root), event emission (emit), RunState (join arrivals + end results), and the builder.
context.rsWorkflowContext: the state document under RwLock<Value> (with_state, snapshot, set_node_output, set_node_error, node_output), execution id (UUID v7), elapsed clock, blob store handle, atomic event-sequence counter. child_of() builds a subworkflow context: own id and state, shared blob store and event counter.
handlers/Per-kind semantics as impl WorkflowExecutor blocks: event.rs (run_start/run_end), task.rs (run_task), foreach.rs (run_foreach + per-item driver: semaphore concurrency, throttle, collect/fail), gateway.rs (run_gateway + pick_branch), subworkflow.rs (run_subworkflow: child context, child executor, output/error propagation). mod.rs documents the pattern and the add-a-kind checklist.
policy.rsexecute_with_policy: the retry/timeout/panic envelope around every task invocation — attempt loop, backoff_delay (exponential/linear/fixed, overflow-safe), tokio::time::timeout per attempt, catch_unwind → TASK_PANIC via panic_error. Unit-tested in isolation.
graph.rs (pub(crate))GraphIndex: prebuilt adjacency (outgoing by trigger, incoming counts, node lookup) so traversal never scans Vec<FlowEdge>.
schemas.rs (pub(crate))CompiledSchemas: every JSON Schema in the document and the referenced task manifests, compiled once at build (INVALID_SCHEMA on failure) and reused on every run.
registry.rsWorkflowRegistry: shared name→definition store for subworkflows (WORKFLOW_NAME_CONFLICT on duplicates).

Construction (build_internal) — the order matters

  1. Scoped profiles: if the document has inline tasks, a scoped copy of the registry is created and profiles registered into it (resolving $secret via the provider). The shared registry is never polluted; children are built with the original registry, so inline profiles stay local to their document.
  2. validate_with (built-ins + host rules) and validate_tasks (every referenced task id exists in the registry).
  3. CompiledSchemas::build and GraphIndex::build.
  4. Subworkflow resolution: each subworkflow node resolves its name (inline section first, shared registry second) and the child executor is built recursively right here, carrying an ancestry stack to detect cycles (SUBWORKFLOW_CYCLE) and a depth cap of 8 (SUBWORKFLOW_DEPTH_EXCEEDED). Child errors bubble up prefixed with the child's name. A missing name is SUBWORKFLOW_NOT_FOUND — at build, never at runtime.

Traversal & the failure ladder

  • execute_from(node) dispatches on NodeKind to the handler; handlers return the node result; continue_through fans out over outgoing normal edges (try_join_all for parallelism).
  • Join nodes accumulate arrivals in RunState::joins under a mutex; the last arrival continues the flow.
  • after_task_result implements the ladder: success → continue; error + on: error edge → publish $.nodes.<id>.error, emit node_failed(error_routed=true), continue through the error edge; panic + on: panic edge → same through panic edges; otherwise the run fails.
  • End of run: RunState::ends holds the end-node results; no end reached → NO_OUTPUT; pending joins → JOIN_INCOMPLETE. Only the root execution cleans up the blob store.

4.5 task/ — the extension contract

#[async_trait]
pub trait Task: Send + Sync + 'static {
    fn manifest(&self) -> &TaskManifest;   // id, description, input/output JSON Schemas
    async fn execute(&self, ctx: &WorkflowContext, input: WorkflowData) -> WorkflowResult;
}
  • TaskManifest is serializable: the full catalog of available tasks can be exported as JSON and used by external tooling (designers, validators) without the engine.
  • TaskRegistry (registry.rs): thread-safe id→task map. scoped() produces a copy-on-write child registry used for inline profiles. register_profile(profile, secrets) resolves $secret references in bind and wraps the base task.
  • ProfileTask (profile.rs): the derived task that executes a profile — validate against the profile's input schema → apply_shape(bind, input) → run the base task (PROFILE_BIND_INVALID if the base rejects the bound input) → apply_shape(output, base_output) → validate against the profile's output schema. Once registered, indistinguishable from any other task.
  • WorkflowData is a thin newtype over serde_json::Value with Deref and From conversions; WorkflowResult = Result<WorkflowData, WorkflowError>.

4.6 io/ — host resources

Blobs (blob.rs)

#[async_trait]
pub trait BlobStore: Send + Sync + 'static {
    async fn put(&self, data: Vec<u8>, name: Option<String>) -> Result<BlobRef, _>;
    async fn get(&self, blob: &BlobRef) -> Result<Vec<u8>, _>;
    async fn import_file(&self, path: &Path, name: Option<String>) -> Result<BlobRef, _>;
    fn local_path(&self, blob: &BlobRef) -> Result<PathBuf, _>;   // streaming consumers
    async fn cleanup(&self) -> Result<(), _>;
}

pub trait BlobStoreFactory: Send + Sync {
    fn create(&self, execution_id: &str) -> Arc<dyn BlobStore>;
}
  • The injectable thing is the factory, not a store: stores have per-execution lifecycle (created with the execution id, cleaned by the root run).
  • TempDirBlobStore (v1 default): one temp directory per execution, lazily created, removed on cleanup and on Drop as a safety net. Blob ids are store-generated UUID v7; blob_path rejects any id that is not alphanumeric/dash — forged references (path traversal) are INVALID_BLOB_ID.
  • Streaming contract: producers write to a temp file then import_file; consumers read via local_path. put/get are the convenience whole-buffer pair.

Secrets (secret.rs)

pub trait SecretProvider: Send + Sync {
    fn get(&self, name: &str) -> Option<String>;
}
pub fn resolve_secrets(value: &mut Value, provider: &dyn SecretProvider) -> Result<(), _>

resolve_secrets walks a JSON document replacing every single-key {"$secret": "NAME"} object with the provider's value (SECRET_NOT_FOUND if absent; objects with extra keys are left untouched). It is called at profile registration — secrets exist in memory inside baked profile configs, never in the serialized document.

4.7 observe/ — observability

  • ExecutionObserver::on_event(&ExecutionEvent) — called synchronously from the executor. The contract demands non-blocking implementations; slow sinks must buffer.
  • ExecutionEvent: execution_id, optional parent_execution_id, seq (atomic counter shared with subworkflows → total order over the whole execution tree), elapsed_ms, flattened EventKind (type snake_case tag in JSON).
  • EventKind: workflow_started/completed/failed, node_started/completed/failed (with error_routed), task_attempt_started (resolved input on attempt 1 only) / task_attempt_failed (will_retry, next_delay_ms), foreach_item_completed/failed.
  • The JSON encoding is stable by design: events are intended to become the journal of a future durable executor (event sourcing) without redesign. Add variants; never change existing ones.
  • history.rs: InMemoryHistory (the built-in observer) and ExecutionReport/NodeReport — a per-node status/attempts/duration summary derived purely from events. report() covers the root execution; report_for(id) a specific one; executions() lists the tree.

4.8 error/ — the failure contract

  • WorkflowError (mod.rs): code + message + optional source_task + optional boxed source. Serializable; travels in events and node error documents.
  • codes.rs: the catalog — ~50 documented pub const strings grouped by phase (definition / construction / expressions / execution / host resources), plus ALL for tooling and a uniqueness test. Convention: FAMILY_DETAIL in SCREAMING_SNAKE_CASE; the constant's value equals its name.
Codes are public contract. They are matched by host code and stored in persisted events. Never rename or repurpose one — only add. New codes go into codes.rs with a doc comment and into ALL.

6. Extension Points

This is the expanded version of the "Where do I add…?" table in lib.rs.

6.1 A new task / extension crate

  1. Create crates/extensions/<name> as workflow-forge-ext-<name>, depending on workflow-forge-core.
  2. Implement Task for each unit of work. Use namespaced ids ("<name>.<task>"). Build schemas with the re-exported workflow_forge_core::schemars (no direct schemars dependency needed).
  3. Expose a pub fn register(registry: &TaskRegistry) registering every task.
  4. Wire into the facade: feature flag in crates/forge/Cargo.toml + the conditional call in register_extensions().
pub struct Reverse { manifest: TaskManifest }

impl Reverse {
    pub fn new() -> Self {
        Self { manifest: TaskManifest {
            id: "text.reverse".into(),
            description: Some("Reverses a string".into()),
            input_schema: Some(/* {"type":"object","required":["text"], …} */),
            output_schema: Some(/* {"type":"string"} */),
        } }
    }
}

#[async_trait]
impl Task for Reverse {
    fn manifest(&self) -> &TaskManifest { &self.manifest }
    async fn execute(&self, _ctx: &WorkflowContext, input: WorkflowData) -> WorkflowResult {
        let text = input["text"].as_str().unwrap_or_default();  // schema already enforced it
        Ok(json!(text.chars().rev().collect::<String>()).into())
    }
}

Rules of the contract:

  • The engine validates input/output against your schemas around execute — inside it you may trust the schema.
  • Return WorkflowError with a specific, documented code for every failure mode (extension codes live with the extension, e.g. HTTP_STATUS_ERROR).
  • Reach files only through ctx.blobs() — never the filesystem directly. Stream large payloads via import_file / local_path.
  • Don't panic. A panic is caught and reported as TASK_PANIC, but it is treated as a bug: no retry, no on: error routing.
  • Don't block: execute runs on the Tokio runtime; use async I/O or spawn_blocking for CPU-bound work.

6.2 A new condition operator ("reserved word")

use workflow_forge_core::expr::operators::{self, ConditionOperator};

struct Between;
impl ConditionOperator for Between {
    fn key(&self) -> &'static str { "between" }
    fn evaluate(&self, value: Option<&Value>, operand: &Value)
        -> Result<bool, WorkflowError> {
        let (Some(v), Some(range)) = (value.and_then(Value::as_f64), operand.as_array())
            else { return Ok(false) };
        let (Some(lo), Some(hi)) = (range.first().and_then(Value::as_f64),
                                    range.get(1).and_then(Value::as_f64))
            else { return Ok(false) };
        Ok(lo <= v && v <= hi)
    }
}

// at host startup, BEFORE building any executor:
operators::global().register(Between);
  • Keys must not collide with the 13 spec operators (those never reach Custom).
  • Handle value: None (unresolved path) deliberately; returning false matches built-in behavior.
  • Register at startup so the KnownConditionOperators validation rule sees it — otherwise documents using the operator fail to build.
  • For isolated vocabularies (e.g. multi-tenant hosts), build a private OperatorRegistry and use evaluate_with — but note the executor's gateway evaluation uses the global registry in v1.

6.3 A new validation rule

struct NoHttpUrls;
impl ValidationRule for NoHttpUrls {
    fn codes(&self) -> &'static [&'static str] { &["HOST_INSECURE_URL"] }
    fn check(&self, workflow: &WorkflowDefinition,
             _ctx: &ValidationCtx<'_>, errors: &mut Vec<WorkflowError>) {
        // walk workflow.nodes, push WorkflowError per violation — accumulate, don't stop
    }
}

let executor = WorkflowExecutor::builder(wf, registry)
    .rule(NoHttpUrls)
    .build()?;
  • Host rules run after the built-ins, also over every subworkflow (inline or registry).
  • Declare your codes in codes(). Host-specific codes live in the host; engine codes go through error::codes.
  • A built-in rule instead goes in validate/rules/<area>.rs, gets appended to rules::BUILTIN, declares catalog codes, and ships with its own tests.

6.4 A new blob store (e.g. S3)

struct S3Factory { bucket: String, client: aws_sdk_s3::Client }
impl BlobStoreFactory for S3Factory {
    fn create(&self, execution_id: &str) -> Arc<dyn BlobStore> {

// implement BlobStore for S3Store: put/get/import_file/local_path/cleanup

builder.blobs(Arc::new(S3Factory { … }))
  • Keep the per-execution lifecycle: namespace objects by execution_id; cleanup() removes the whole namespace.
  • Generate ids yourself (UUID v7 recommended) and validate them in lookups — the id check is your forgery defense.
  • local_path is the streaming contract; a remote store may materialize to a temp file. (v1 assumes file-backed blobs.)

6.5 A new secret provider

struct VaultSecrets { client: VaultClient }
impl SecretProvider for VaultSecrets {
    fn get(&self, name: &str) -> Option<String> { self.client.read(name).ok() }
}

builder.secrets(&vault)   // note: borrowed, must outlive the build call

The provider is only consulted during build (profile registration). It is synchronous by design; wrap async vault clients with a blocking handle or pre-fetch.

6.6 A new observer

struct PgObserver { tx: tokio::sync::mpsc::UnboundedSender<ExecutionEvent> }
impl ExecutionObserver for PgObserver {
    fn on_event(&self, event: &ExecutionEvent) {
        let _ = self.tx.send(event.clone());   // never block here
    }
}

One observer instance receives the whole execution tree (the executor propagates it to subworkflow children). Reconstruct ordering with seq; group with execution_id / parent_execution_id.

6.7 A new node kind — a spec change

This is deliberately heavier than the other extension points, because it changes the language every consumer must understand. The checklist (also in runtime/handlers/mod.rs):

  1. spec/node/<kind>.rs: the node struct (serde) + variant in NodeKind + arm in NodeKind::name().
  2. runtime/handlers/<kind>.rs: an impl WorkflowExecutor block with run_<kind>; declare the module in handlers/mod.rs; add the dispatch arm in executor.rs::execute_from.
  3. validate/rules/: structural rules for the kind + appended to rules::BUILTIN; new codes documented in error/codes.rs + ALL.
  4. Decide event semantics (observe::EventKind — new variant if node/task events don't fit).
  5. Tests: rule tests, handler integration test under crates/core/tests/, and a spec-document example.
  6. Bump the spec discussion: if 1.0 documents must not break, the kind belongs to a future spec version (SUPPORTED_SPECS).

8. Invariants & Gotchas

  • Error codes never change value. Add, never rename. codes.rs is the single source of truth; its uniqueness test and the rules-vs-catalog test enforce hygiene.
  • Event JSON is stable. The type tags and field names of EventKind are persisted by hosts and earmarked as the future durable journal. Additive changes only.
  • Identifiers are UUID v7 (Uuid::now_v7()) — time-ordered, index-friendly. Never v4.
  • Mappings error on absence; shapes and conditions tolerate it. $.-absence is MAPPING_PATH_NOT_FOUND; @.-absence is null; condition-path absence is false. Don't "fix" one to behave like another — documents rely on it.
  • Panic ≠ error. policy.rs converts panics to TASK_PANIC, which skips retry and on: error routing by design — a bug must not be retried into a side-effecting API.
  • Inline profiles are scoped. build_internal registers them into registry.scoped(), and children get the original registry. Breaking this leaks document-local definitions across tenants.
  • Secrets resolve at registration, not at run. The serialized document never holds secret values; the in-memory baked profile does. Keep it that way.
  • Blob ids are validated. TempDirBlobStore::blob_path rejects non-UUID-shaped ids — that's the path-traversal defense. Any new store needs the same property.
  • Subworkflows share the root blob store and event counter but have their own state document and execution id. Cleanup belongs only to the root run.
  • Graph rules self-disable on broken references. Reachability/Acyclicity check for prior UNKNOWN_NODE_REF errors before running — they read the shared error vector. Rule order in BUILTIN matters.
  • Observer calls are synchronous on the execution's hot path. Anything slow inside on_event slows the workflow.
  • Register operators before building executors, or KnownConditionOperators will reject documents that would work at runtime.

9. Conventions

  • Docs are enforced: #![warn(missing_docs)] in lib.rs; every public item carries a doc comment; every module a //! header explaining what/how/why. The crate-level doc in lib.rs holds the family map and the "Where do I add…?" quick table — keep both in sync with reality.
  • Spec types stay logic-free. Evaluation goes to expr, checking to validate, execution to runtime. If you're adding a method with behavior to a spec struct, you're probably in the wrong family.
  • One JSONPath funnel. All path queries go through expr::path::query_first. Don't call jsonpath_rust anywhere else.
  • Errors are codes + helpful messages. Messages name the offending node/edge/operator and, where possible, what was expected. Use .with_source_task(node_id) whenever a node is known.
  • Terminology: the crates under crates/extensions/ are called extensions (never "plugins").
  • Validation accumulates. Rules push into the shared vector and keep going. Anything that aborts at the first error is a regression.
  • Build-time over runtime. When adding a feature, ask first: can its misuse be detected by a validation rule or at build_internal? Runtime errors are the fallback, not the default.
