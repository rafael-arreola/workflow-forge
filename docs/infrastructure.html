workflow-forge — Infrastructure Manual

The engineering reference for maintaining, extending and improving the workflow-forge engine. It documents every component of the core, how each one works internally, and how they assemble and communicate to behave as specified. Diagrams are interactive — click any diagram to open it in a zoomable viewer. If you only want to use the library, read the User Manual instead.

1. Purpose & Scope

The engine (crates/core, package workflow-forge-core) executes workflow documents conforming to spec 1.0. Its architecture pursues four goals, in this order:

  1. Extensible — every behavior a host might want to change is behind a trait with a registration point; the engine knows no concrete task, storage, or operator in advance.
  2. Curable — responsibilities are closed per module ("family"); a bug in gateway routing can only live in a handful of known files.
  3. Testable — every unit (rule, operator, handler, policy) is testable in isolation; behavior is locked by ~160 tests across the workspace.
  4. Documented — #![warn(missing_docs)] is enforced; every module opens with a //! header stating what it does, how, and why.

3. Core Architecture

3.1 The family graph

The core is organized in eight families with closed responsibilities. Dependencies flow strictly in one direction — spec depends on nothing, runtime depends on everything. There are no dependency cycles between families; that is what keeps each one curable in isolation.

3.2 The trait & dependency-injection map

Seven traits define every seam where the host can replace behavior. The executor owns them as trait objects; nothing in the core ever names a concrete implementation except the defaults.

Builder methodTrait injectedConsumed whenDefault

.workflows()runtime::WorkflowRegistryBuild only — subworkflow names resolve to child executorsnone

.observer()observe::ExecutionObserverEvery run — synchronous per event; propagated to all child executorsnone
.rule()validate::ValidationRuleBuild only — after built-ins, also on every subworkflowrules::BUILTIN only

Two more extension surfaces are registries rather than builder arguments: task::TaskRegistry (tasks and profiles — consulted at build for validate_tasks/CompiledSchemas and at run for dispatch) and expr::operators::global() (condition operators, process-wide OnceLock, consulted at build by the KnownConditionOperators rule and at run by gateway evaluation).

A deliberate non-trait: node kinds. spec::node::NodeKind is a closed enum — the node vocabulary belongs to the spec, not to hosts. Engine extensibility flows through tasks, not through new kinds. The per-kind execution logic is organized as impl WorkflowExecutor blocks in separate files (runtime/handlers/), which gives the same modularity as a NodeHandler trait without dynamic-dispatch ceremony for a vocabulary that cannot grow at runtime. Adding a kind is a spec change with a documented checklist (§7.7).

Concurrency primitives in play: futures::future::try_join_all (parallel edges and gateway fan-out — first error cancels siblings by drop), futures::stream::buffered(n) (foreach concurrency window), tokio::time::timeout (per attempt), tokio::time::sleep (backoff and throttle), catch_unwind (panic isolation). Recursion through the graph returns BoxFuture (execute_from) because async recursion needs boxing; the same applies to foreach_item, where rustc cannot prove Send for the unboxed closure chain.

4. Assembly: Building an Executor

Construction is where the engine earns its "fail at build, not at run" promise. WorkflowExecutor::builder(…).build() funnels into build_internal (runtime/executor.rs), which assembles five components in a fixed order — each step depends on guarantees established by the previous one:

Step by step, and why the order matters

  1. Scoped profile registration. If the document declares inline tasks, the builder calls registry.scoped() — a copy-on-write child registry — and registers each TaskProfile into it, resolving {"$secret": …} references through the injected SecretProvider at this moment. Two consequences: the shared registry is never polluted by document-local definitions, and secrets exist only inside the in-memory baked profile, never in any serialized form. The original registry is kept aside (original_registry) because children must not see the parent's inline profiles.
  2. Structural validation. validate_with(workflow, host_rules) runs rules::BUILTIN in order, then host rules, all pushing into one shared Vec<WorkflowError> — and recurses into inline subworkflow documents. validate_tasks(workflow, registry) then checks every task/foreach reference against the (scoped) registry. This must run after step 1 — otherwise nodes referencing inline profiles would report false TASK_NOT_FOUND.
  3. CompiledSchemas::build. Walks the nodes once and compiles: the schema of each start/end node (keyed by NodeId) and the input_schema/output_schema of each referenced task manifest (keyed by TaskId, deduplicated). Schemas are static per definition — compiling them per node execution (and per retry) would be repeated work. A non-compiling schema is INVALID_SCHEMA at build. Needs step 1 (profile manifests must exist in the registry).
  4. GraphIndex::build. One pass over workflow.edges sorts every edge into four buckets keyed by source node: outgoing (normal flow), outgoing_error (on: error), outgoing_panic (on: panic), plus incoming_count (normal-flow in-degree, the join arrival target) and the start node id. After this, traversal never scans the edge list — every hop is a HashMap lookup. The expect() calls inside (node(), start lookup) are safe because step 2 already guaranteed referential integrity; this is the first place the build order turns validation into license for infallible code.
  5. Recursive subworkflow resolution. For each subworkflow node: resolve the name against the document's inline workflows section first, then the shared WorkflowRegistry; missing → SUBWORKFLOW_NOT_FOUND. The child executor is built by calling build_internal recursively right here, passing: the original registry (profile scoping), the same secrets provider and host rules, and an ancestry: Vec<String> stack of workflow names. If the child's name is already in the stack → SUBWORKFLOW_CYCLE (message shows the chain a → b → c); stack depth ≥ 8 → SUBWORKFLOW_DEPTH_EXCEEDED. Child build errors bubble up with their messages prefixed "in sub-workflow '<name>': …". The resolved children land in subworkflows: HashMap<NodeId, WorkflowExecutor> — at runtime, dispatch is a map lookup, never a registry search.

Finally the builder applies the optional injections: blobs replaces the default TempDirBlobFactory, and observer is set via set_observer, which walks subworkflows recursively cloning the Arc into every child — that is how one observer sees the whole execution tree.

5. The Families in Depth

5.1 spec/ — the language

Pure data, zero logic. Everything here is serde types mirroring the JSON document. If a struct in spec needs behavior beyond (de)serialization and trivial accessors, that behavior belongs in another family — evaluation goes to expr, checking to validate, execution to runtime.

FileContains

node/mod.rsNodeId, Node (id + #[serde(flatten)] kind), NodeKind enum (closed; kind is the JSON tag; name() returns the discriminator string), SubworkflowNode

profile.rsTaskProfile — the declarative profile definition (id, extends, schemas, bind, output). The executable counterpart lives in task::profile.

Hand-written serde, on purpose

Three deserializers are manual, all for the same reason — error quality and open vocabulary:

  • Condition: an untagged derive produces the useless "data did not match any variant"; the manual impl reports exactly which key is missing or extraneous ("expected 'and', 'or', 'not' or a comparison with 'path'; keys found: [foo]") and rejects logical keys with siblings.
  • Comparison: pops path out of the object, then demands exactly one remaining key — the operator. More or fewer keys produce a message that lists what was found.
  • CompareOp::from_key_operand(key, operand): the 13 spec keys are matched and their operand types verified at parse time (in wants an array, exists/is_null a bool, starts_with/ends_with/matches a string). Any unknown key becomes CompareOp::Custom — this is the deserialization half of the extensible operator vocabulary; the evaluation half lives in expr::operators. Serialization (key() + operand()) round-trips Custom keys verbatim, so documents with host operators survive load→save unchanged.

5.2 expr/ — expression resolution

Three resolution dialects, one path engine. The crucial assembly fact: every JSONPath query in the entire engine funnels through expr::path::query_first — mappings, shapes, and condition paths included. Changing path semantics (or swapping the JSONPath library) is a one-file change.

The operator registry — anatomy

pub trait ConditionOperator: Send + Sync + 'static {
    fn key(&self) -> &'static str;
    fn evaluate(&self, value: Option<&Value>, operand: &Value)
        -> Result<bool, WorkflowError>;
}

pub struct OperatorRegistry {            // RwLock<HashMap<String, Arc<dyn ConditionOperator>>>
    pub fn register(&self, op)           // overwrites same key
    pub fn get / contains / list
}
pub fn global() -> &'static OperatorRegistry   // OnceLock, process-wide

Evaluation walks the condition tree: And short-circuits on the first false, Or on the first true, Not inverts, Compare resolves path via query_first and dispatches on CompareOp. Built-in semantics are a single match; Custom { key, operand } does registry.get(key) → op.evaluate(value, operand), or UNKNOWN_CONDITION_OPERATOR if unregistered (the validation rule catches this at build first). evaluate() uses global(); evaluate_with(context, registry) takes an explicit registry for tests and isolated vocabularies.

Absence contract — operators receive value: None when the path did not resolve and decide their own semantics. Built-ins return false (except exists, which answers the question directly). Operators must only fail on definition errors (bad regex, bad path), never on data.

5.3 validate/ — the rule pipeline

Everything detectable before execution is detected here. Validation is a pipeline of rules sharing one error vector that accumulates — a document gets fixed in one pass, never error-by-error.

pub trait ValidationRule: Send + Sync {
    fn codes(&self) -> &'static [&'static str];  // living documentation, test-enforced
    fn check(&self, workflow: &WorkflowDefinition,
             ctx: &ValidationCtx<'_>, errors: &mut Vec<WorkflowError>);
}

The communication mechanics that make the pipeline work:

  • ValidationCtx<'w> (context.rs) is built once per document and borrowed by every rule: node lookup map, outgoing/incoming edge indexes, and the start-node list. Rules never re-scan workflow.edges.
  • rules::BUILTIN: &[&dyn ValidationRule] fixes execution order. Host rules (from builder().rule(…)) are chained after built-ins: BUILTIN.iter().chain(extra).
  • The shared error vector is also a communication channel between rules. Reachability and Acyclicity inspect errors for a prior UNKNOWN_NODE_REF and self-disable — BFS/Kahn over a graph with dangling references would only produce noise. This is why rule order in BUILTIN is part of the design: structural rules first, graph analysis last.
  • validate_with recurses into the document's inline workflows with the same rule set, prefixing child errors with "in the inline sub-workflow '<name>': …".
  • validate_tasks(workflow, registry) is deliberately a separate function: it is the only check that needs the TaskRegistry, so pure-document validation (validate()) stays usable by tooling without a registry.

5.5 task/ — the extension contract

#[async_trait]
pub trait Task: Send + Sync + 'static {
    fn manifest(&self) -> &TaskManifest;   // id, description, input/output JSON Schemas
    async fn execute(&self, ctx: &WorkflowContext, input: WorkflowData) -> WorkflowResult;
}

How the pieces connect:

  • TaskManifest is serializable: the full catalog of available tasks can be exported as JSON and consumed by external tooling (designers, validators) without the engine. CompiledSchemas reads the manifest schemas at build; policy.rs enforces them at run.
  • TaskRegistry (registry.rs): thread-safe id→Arc<dyn Task> map. scoped() produces the copy-on-write child used for inline profiles (§4 step 1). register_profile(profile, secrets) checks extends exists (PROFILE_BASE_NOT_FOUND), the id is free (PROFILE_ID_CONFLICT), resolves $secret in bind, and inserts a ProfileTask.
  • ProfileTask (profile.rs) is the adapter pattern in miniature — it wraps the base Arc<dyn Task> and implements Task itself: execute = apply bind shape to the profile input → call the base (a base-side schema rejection becomes PROFILE_BIND_INVALID) → apply output shape to the base output. Its manifest carries the profile's own schemas, so CompiledSchemas/policy validate the profile contract at the boundary. Once registered, callers cannot distinguish a profile from a hand-written task.
  • WorkflowData is a newtype over serde_json::Value (Deref + From both ways); WorkflowResult = Result<WorkflowData, WorkflowError>. It marks the engine↔extension boundary in signatures.

5.6 io/ — host resources

Blobs (blob.rs)

  • The injectable thing is the factory, not a store: stores have per-execution lifecycle (created with the execution id, cleaned by the root run). TempDirBlobFactory is the default.
  • TempDirBlobStore: one temp directory per execution (workflow-forge-<execution_id>), lazily created on first write, removed on cleanup() and on Drop as a safety net. Ids are store-generated UUID v7; blob_path rejects any id that is not alphanumeric/dash — forged references (path traversal like ../../etc/passwd) are INVALID_BLOB_ID before touching the filesystem.
  • Streaming contract: producers write to a temp file then import_file (a copy into the store); consumers read via local_path and stream from disk. put/get are the whole-buffer convenience pair for small payloads.

Secrets (secret.rs)

pub trait SecretProvider: Send + Sync {
    fn get(&self, name: &str) -> Option<String>;
}
pub fn resolve_secrets(value: &mut Value, provider: &dyn SecretProvider) -> Result<(), _>

resolve_secrets walks a JSON document in place, replacing every single-key {"$secret": "NAME"} object with the provider's value (SECRET_NOT_FOUND if absent; objects with extra keys are deliberately left untouched — they are data, not references). It is called exactly once per profile, at registration during build: secrets live only in the in-memory baked profile config, never in the serialized document, never re-fetched per run.

5.7 observe/ — observability

  • emit(ctx, kind) (executor.rs) is the single emission point: it stamps execution_id, parent_execution_id, seq (via ctx.next_event_seq()) and elapsed_ms, then calls observer.on_event — a no-op if no observer is registered.
  • EventKind serializes with a snake_case type tag: workflow_started/completed/failed, node_started/completed/failed (with error_routed), task_attempt_started (resolved input on attempt 1 only — retries reuse it) / task_attempt_failed (will_retry, next_delay_ms), foreach_item_completed/failed. The JSON encoding is stable by design: events are earmarked as the journal of a future durable executor (event sourcing). Add variants; never change existing ones.
  • InMemoryHistory is the built-in observer (a Mutex<Vec>); events() returns them sorted by seq. ExecutionReport::from_events folds events into per-node status (running/completed/failed/error_routed), attempts and durations — derived purely from events, which doubles as a proof that the event stream is sufficient to reconstruct an execution.

5.8 error/ — the failure contract

  • WorkflowError (mod.rs): code + message + optional source_task + optional boxed source. Serializable; it travels in events, in $.nodes.<id>.error, and as the error-edge token.
  • codes.rs: the catalog — ~50 documented pub const strings grouped by phase (definition / construction / expressions / execution / host resources), plus ALL for tooling and a uniqueness test. Convention: FAMILY_DETAIL in SCREAMING_SNAKE_CASE; the constant's value equals its name.
Codes are public contract. They are matched by host code (err.code == codes::TASK_PANIC drives the panic-routing decision inside the engine itself) and stored in persisted events. Never rename or repurpose one — only add. New codes go into codes.rs with a doc comment and into ALL.

6. Life of an Execution

6.1 The traversal engine

run(trigger) creates the WorkflowContext (execution id, state document, blob store), wraps run_with_ctx (which emits workflow_started/completed/failed around run_inner), and — root only — cleans up blobs. run_inner allocates the per-run RunState { joins, ends } on the stack and kicks off execute_from(start, Arc(trigger), None, …).

Key mechanics of execute_from / continue_through (executor.rs):

  • Signature: execute_from(node_id, carried: Arc<Value>, origin: Option<NodeId>, ctx, state) -> BoxFuture. carried is the predecessor's output (the token); origin identifies the predecessor — joins need it to label arrivals. The future is boxed because graph traversal is async recursion.
  • Dispatch is a single match on NodeKind: start/end → event.rs; task/foreach/subworkflow → their handler, then after_task_result (the three "task-executing" kinds share the failure ladder); gateway → gateway.rs (it manages its own continuation).
  • continue_through(edges, carried, …): zero edges → branch ends; one edge → tail call; N edges → try_join_all, cloning only the Arc. First error cancels sibling branches (dropping their futures) — the engine is fail-fast across parallel branches.
  • Node events: node_started is emitted on entry — except for joins, which "start" once per arrival; their started+completed pair is emitted when the join completes.
  • End of run: RunState.ends drives the result — 0 ends reached → NO_OUTPUT; 1 → its value; several (parallel branches reaching different ends) → an object keyed by end-node id. Leftover entries in RunState.joins are starved joins: if no end was reached they become a JOIN_INCOMPLETE error whose message lists received k/n branches (arrived: […]) per join; if an end was reached they are logged as a warning.

6.2 The failure ladder

Upstream of the ladder, policy.rs::execute_with_policy is the shared envelope for every extension invocation (task nodes with emit_attempts: true, foreach elements with false — elements have their own item events). Its loop, precisely:

  1. Validate input against the precompiled input validator → TASK_INPUT_INVALID (no attempt happens).
  2. Per attempt: wrap task.execute in AssertUnwindSafe(…).catch_unwind(); if timeout_ms is set, wrap that in tokio::time::timeout. Outcomes: output / task error / TASK_TIMEOUT / TASK_PANIC (payload downcast to &str/String for the message). AssertUnwindSafe is sound because a panicked attempt's result is discarded and engine state only mutates via the executor after a success.
  3. On success: validate output → TASK_OUTPUT_INVALID (not retried — a contract violation is a bug, not a transient).
  4. On failure: fill source_task if empty; retry iff code != TASK_PANIC and attempt <= retry.max; compute backoff_delay (exponential initial·2^(n−1) / linear initial·n / fixed, all saturating_* against overflow); emit task_attempt_failed; sleep; loop.

6.3 Foreach mechanics

Implementation notes worth knowing before touching this file:

  • The throttle gate spaces element starts, not completions, and holds under concurrency: each element locks the Mutex<Instant>, reserves start_at = max(next, now), advances next = start_at + throttle, releases the lock, then sleeps — the critical section never contains the sleep.
  • buffered(n) (not buffer_unordered) keeps results in input order, which is what makes the fail output a positionally-stable array.
  • Each element future is boxed (BoxFuture) because rustc cannot prove Send for the unboxed async closure chain inside the recursive executor.
  • In collect mode a TASK_PANIC still aborts the node: collect tolerates data failures, not extension bugs.

6.4 Parallel & join mechanics

The join's output is an object { "<predecessor-id>": <its token>, … } — deterministic regardless of arrival order. This is why execute_from threads origin through the traversal: it is the join's only way to know which branch a token came from. Exclusive gateways, by contrast, are pure routing: pick_branch evaluates branch conditions in declaration order under a single with_state read lock, falls back to the else branch, and the winner's label filters the outgoing edges.

7. Extension Points

This is the expanded version of the "Where do I add…?" table in lib.rs.

7.1 A new task / extension crate

  1. Create crates/extensions/<name> as workflow-forge-ext-<name>, depending on workflow-forge-core.
  2. Implement Task for each unit of work. Use namespaced ids ("<name>.<task>"). Build schemas with the re-exported workflow_forge_core::schemars (no direct schemars dependency needed).
  3. Expose a pub fn register(registry: &TaskRegistry) registering every task.
  4. Wire into the facade: feature flag in crates/forge/Cargo.toml + the conditional call in register_extensions().
pub struct Reverse { manifest: TaskManifest }

impl Reverse {
    pub fn new() -> Self {
        Self { manifest: TaskManifest {
            id: "text.reverse".into(),
            description: Some("Reverses a string".into()),
            input_schema: Some(/* {"type":"object","required":["text"], …} */),
            output_schema: Some(/* {"type":"string"} */),
        } }
    }
}

#[async_trait]
impl Task for Reverse {
    fn manifest(&self) -> &TaskManifest { &self.manifest }
    async fn execute(&self, _ctx: &WorkflowContext, input: WorkflowData) -> WorkflowResult {
        let text = input["text"].as_str().unwrap_or_default();  // schema already enforced it
        Ok(json!(text.chars().rev().collect::<String>()).into())
    }
}

Rules of the contract:

  • The engine validates input/output against your schemas around execute (in policy.rs, using precompiled validators) — inside it you may trust the schema.
  • Return WorkflowError with a specific, documented code for every failure mode (extension codes live with the extension, e.g. HTTP_STATUS_ERROR).
  • Reach files only through ctx.blobs() — never the filesystem directly. Stream large payloads via import_file / local_path.
  • Don't panic. A panic is caught and reported as TASK_PANIC, but it is treated as a bug: no retry, no on: error routing.
  • Don't block: execute runs on the Tokio runtime; use async I/O or spawn_blocking for CPU-bound work.

7.2 A new condition operator ("reserved word")

use workflow_forge_core::expr::operators::{self, ConditionOperator};

struct Between;
impl ConditionOperator for Between {
    fn key(&self) -> &'static str { "between" }
    fn evaluate(&self, value: Option<&Value>, operand: &Value)
        -> Result<bool, WorkflowError> {
        let (Some(v), Some(range)) = (value.and_then(Value::as_f64), operand.as_array())
            else { return Ok(false) };
        let (Some(lo), Some(hi)) = (range.first().and_then(Value::as_f64),
                                    range.get(1).and_then(Value::as_f64))
            else { return Ok(false) };
        Ok(lo <= v && v <= hi)
    }
}

// at host startup, BEFORE building any executor:
operators::global().register(Between);
  • Keys must not collide with the 13 spec operators (those never reach Custom).
  • Handle value: None (unresolved path) deliberately; returning false matches built-in behavior.
  • Register at startup so the KnownConditionOperators validation rule sees it — otherwise documents using the operator fail to build.
  • For isolated vocabularies (e.g. multi-tenant hosts), build a private OperatorRegistry and use evaluate_with — but note the executor's gateway evaluation uses the global registry in v1.

7.4 A new blob store (e.g. S3)

impl BlobStoreFactory for S3Factory {

7.6 A new observer

struct PgObserver { tx: tokio::sync::mpsc::UnboundedSender<ExecutionEvent> }
impl ExecutionObserver for PgObserver {
    fn on_event(&self, event: &ExecutionEvent) {
        let _ = self.tx.send(event.clone());   // never block here
    }
}

One observer instance receives the whole execution tree (the executor propagates the Arc to every child at registration). Reconstruct ordering with seq; group with execution_id / parent_execution_id. on_event runs synchronously on the execution hot path — hand off through a channel.

7.7 A new node kind — a spec change

This is deliberately heavier than the other extension points, because it changes the language every consumer must understand. The checklist (also in runtime/handlers/mod.rs):

  1. spec/node/<kind>.rs: the node struct (serde) + variant in NodeKind + arm in NodeKind::name().
  2. runtime/handlers/<kind>.rs: an impl WorkflowExecutor block with run_<kind>; declare the module in handlers/mod.rs; add the dispatch arm in executor.rs::execute_from. Decide whether the kind "executes work" — if so, route its result through after_task_result to inherit retry-error-panic routing for free.
  3. validate/rules/: structural rules for the kind + appended to rules::BUILTIN; new codes documented in error/codes.rs + ALL.
  4. If the kind affects edges or in-degrees, revisit GraphIndex::build and the join arithmetic.
  5. Decide event semantics (observe::EventKind — new variant if node/task events don't fit).
  6. Tests: rule tests, handler integration test under crates/core/tests/, and a spec-document example.
  7. Bump the spec discussion: if 1.0 documents must not break, the kind belongs to a future spec version (SUPPORTED_SPECS).

9. Invariants & Gotchas

  • Error codes never change value. Add, never rename. codes.rs is the single source of truth; its uniqueness test and the rules-vs-catalog test enforce hygiene.
  • Event JSON is stable. The type tags and field names of EventKind are persisted by hosts and earmarked as the future durable journal. Additive changes only.
  • Identifiers are UUID v7 (Uuid::now_v7()) — time-ordered, index-friendly. Never v4.
  • Mappings error on absence; shapes and conditions tolerate it. $.-absence is MAPPING_PATH_NOT_FOUND; @.-absence is null; condition-path absence is false. Don't "fix" one to behave like another — documents rely on it.
  • Panic ≠ error. policy.rs converts panics to TASK_PANIC, which skips retry and on: error routing by design — a bug must not be retried into a side-effecting API, and a half-applied effect must not flow down a compensation path built for clean failures. Foreach collect aborts on panic for the same reason.
  • Validation is a license for expect(). Runtime code unwraps registry lookups, start-node presence and edge references because build-order guarantees them. If you reorder build_internal, you revoke those licenses — audit every expect("validación …").
  • Inline profiles are scoped. build_internal registers them into registry.scoped(), and children get the original registry. Breaking this leaks document-local definitions across tenants.
  • Secrets resolve at registration, not at run. The serialized document never holds secret values; the in-memory baked profile does. Keep it that way.
  • Blob ids are validated. TempDirBlobStore::blob_path rejects non-UUID-shaped ids — that's the path-traversal defense. Any new store needs the same property.
  • Subworkflows share the root blob store and event counter (one Arc clone each in child_of) but have their own state document and execution id. Cleanup belongs only to the root run.
  • Graph rules self-disable on broken references. Reachability/Acyclicity read the shared error vector for prior UNKNOWN_NODE_REF. Rule order in BUILTIN matters.
  • The token is an Arc. Parallel fan-out clones the handle, not the payload. If you add a code path that needs an owned Value, use Arc::unwrap_or_clone — don't sprinkle .clone() on the inner value.
  • try_join_all is fail-fast. A failing branch cancels its siblings by drop. If a future kind needs "wait for all even on failure", that's a semantic change to continue_through, not a local fix.
  • Observer calls are synchronous on the execution's hot path. Anything slow inside on_event slows the workflow.
  • Register operators before building executors, or KnownConditionOperators will reject documents that would work at runtime.

10. Conventions

  • Docs are enforced: #![warn(missing_docs)] in lib.rs; every public item carries a doc comment; every module a //! header explaining what/how/why. The crate-level doc in lib.rs holds the family map and the "Where do I add…?" quick table — keep both in sync with reality.
  • Spec types stay logic-free. Evaluation goes to expr, checking to validate, execution to runtime. If you're adding a method with behavior to a spec struct, you're probably in the wrong family.
  • One JSONPath funnel. All path queries go through expr::path::query_first. Don't call jsonpath_rust anywhere else.
  • Errors are codes + helpful messages. Messages name the offending node/edge/operator and, where possible, what was expected. Use .with_source_task(node_id) whenever a node is known.
  • Terminology: the crates under crates/extensions/ are called extensions (never "plugins").
  • Validation accumulates. Rules push into the shared vector and keep going. Anything that aborts at the first error is a regression.
  • Build-time over runtime. When adding a feature, ask first: can its misuse be detected by a validation rule or at build_internal? Runtime errors are the fallback, not the default.
