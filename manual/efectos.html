Errores, reintentos y efectos

Distingue un error conocido de una escritura cuyo resultado no se pudo confirmar antes de decidir si se puede repetir.

Declara lo que la operación hace

ClasificaciónSignificadoEjemplo
Pure / SafeTransformación sin interacción externa que puede repetirse.Normalizar una string.
Read / SafeLectura repetible; su resultado no tiene por qué permanecer constante.Consultar un cliente.
Write / KeyedEl destino deduplica usando una clave estable y garantiza esa semántica.Crear un pedido en un destino con idempotencia comprobada.
Write / UnsafeRepetir puede duplicar el efecto.POST genérico sin contrato de deduplicación.

Keyed exige cooperación del destino. Enviar una cabecera o declarar la bandera en el descriptor no crea esa garantía. Usa la effect_key de la Invocation conforme al contrato del adaptador; no la reemplaces por una clave aleatoria en cada intento.

Errores con certeza explícita

EffectCertaintyQué afirmas
NotAppliedNo se produjo el efecto. No basta con no haber recibido una respuesta.
AppliedEl efecto se produjo, aunque todavía falte un output conforme.
UnknownNo puedes confirmar si se produjo.

El mensaje debe ser seguro: no copies credenciales ni bodies remotos. El motor conserva clase y certeza, además de la identidad lógica y del intento. Un error nuevo NotApplied no borra incertidumbre de un intento anterior.

Reintentar solo cuando está permitido

max_attempts incluye el primer intento. El default es 1 y el máximo depende del host. El backoff elige una demora después de clasificar la seguridad de repetición; no convierte un rechazo de negocio en un fallo transitorio.

SituaciónRespuesta del coordinador
Input/config/mapping inválidoRechazar o fallar sin repetir validación como si fuera I/O transitorio.
Error transitorio/recurso definitivamente NotAppliedPuede repetir si quedan presupuesto y deadline.
Escritura Unknown y UnsafeBloquear; no repetir automáticamente.
Escritura Unknown y Safe/KeyedRepetir solo si el error es elegible y queda presupuesto; conservar la clave.
Applied con output inválidoMantener el efecto y bloquear para obtener un resultado conforme.

Investigar y resolver un run bloqueado

  1. Consulta el estado, identifica la invocación y el intento exactos y conserva la revisión observada.
  2. Si existe EffectInspector, usa inspect_effect. Es una consulta: no aplica una decisión ni escribe el negocio.
  3. Obtén evidencia del destino. Una búsqueda inconclusa no permite declarar que el efecto no existió.
  4. Envía un ReconcileCommand con command_id estable, revisión e intento observados.
  5. Revisa el recibo y el nuevo estado; un conflicto requiere volver a observar, no sobrescribir otra resolución.

EffectEvidence contiene authority, reference y note. ConfirmApplied valida el output. ConfirmNotApplied requiere evidencia y quiescent: true: el intento ya no puede completar tardíamente. RecordInconclusive conserva el bloqueo. StopTracking requiere permiso propio y cierra sin convertir incertidumbre en éxito.

Si el descriptor anuncia reconciliación, el bundle debe aportar el inspector correspondiente a esa revisión. El inspector no recibe el ExecutionStore: las transiciones siguen siendo responsabilidad del coordinador.

Cancelación y deadlines

El contexto entrega un token de cancelación cooperativa a las operaciones. Timeout, panic o desconexión después de despachar una escritura pueden dejar un efecto incierto. Cancelar un run no revierte una transacción del destino. Una compensación, si tu negocio la necesita, es otra operación explícita.
