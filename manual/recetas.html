Recetas para sistemas existentes

Recorre estas recetas en orden o entra por el problema de tu aplicación. Cada ejemplo usa el mismo motor embebido, entradas concretas y una salida comprobable. El host puede ser tu backend, una aplicación de escritorio o un worker Rust; aquí no se inicia ningún servidor del motor.

Dónde vive cada responsabilidad

El host adapta DTOs, autentica, selecciona el workflow y conserva recursos. El workflow describe orden, bindings, decisiones y handlers. Una operación traduce un SDK o una función existente al contrato público; devuelve datos o errores y no elige el siguiente nodo.

1. Una transformación dentro de una llamada

Empieza con una función de negocio que necesita limpiar texto. La integración inicial contiene el programa completo y la dependencia local.

plan se prepara con normalizar.json una vez por composición. execute espera el resultado de esa llamada; una entrada que incumple el schema devuelve un error. No prepara de nuevo el workflow por cada registro.

Programa completo: inicio.rs. Workflow: normalizar.json.

2. Integrarlo en la capa de aplicación existente

Añade una fachada pequeña como Normalizador al estado de tu aplicación. El dueño del arranque conserva EngineRuntime; los handlers reciben clones de esta fachada. Tu controlador existente convierte su DTO a la entrada esperada y llama a normalizar. No necesitas introducir un framework web.

Facade: este struct presenta una función de tu dominio y oculta la selección del plan. Builder: registra implementaciones antes de arrancar. No hace falta un trait nuevo para envolver una sola variante.

El ejemplo completo procesa Ada, Rafael y Grace con dos futures en vuelo y restaura el orden por índice. Ese límite pertenece al lote del host; los límites globales del engine siguen aplicando. Al recibir admission.full, el host aplica su política de presión de carga. No acumules una cola sin límite ni mantengas un mutex tomado alrededor de execute.

AccessContext::trusted("default") es una decisión explícita para esta demostración local. En tu aplicación, construye el contexto desde tu identidad autenticada y política de acceso; no aceptes ese contexto directamente desde un JSON de un cliente.

Programa completo: sistema.rs.

3. Cancelar una llamada y respetar su presupuesto

Conecta una desconexión, una cancelación de usuario o el cierre del host a un CancellationToken. Usa un token hijo por llamada si quieres cancelar una sin detener sus hermanas. El token padre puede detener el conjunto.

El programa usa un timer de cinco segundos: primero solicita cancelación a los 20 ms y después ejecuta otra llamada con deadline de 20 ms. Ambos caminos comprueban un error y cierran el runtime. Los tiempos ilustran el presupuesto, no una promesa de latencia exacta.

Descartar el future de execute también solicita cancelación; no equivale a haber terminado la limpieza. Al cerrar, deja de aceptar entradas, cancela o espera las llamadas según tu política, espera shutdown y revisa forced y pending. Las operaciones Rust deben cooperar con la cancelación y no bloquear el ejecutor.

Programa completo: cancelacion.rs.

4. Adaptar una capacidad de tu sistema

La extensión modulo-saludos es un crate Rust que depende del protocolo. Exporta OperationBundle y declara schemas, revisión, efecto y seguridad de repetición. El workflow conecta la normalización estándar con la operación propia.

Adapter: para usar una función existente, conserva tu cliente o dependencia en el struct de la operación y traduce su respuesta a OperationOutput. Si puede escribir fuera del proceso, declara el efecto y su incertidumbre reales: el ejemplo de saludo es Pure / Safe porque solo construye una string. No copies esas garantías a una escritura HTTP.

Entrada {"nombre":" Rafael "} → salida {"saludo":"Hola, Rafael"}. Consulta el capítulo de módulos para el contrato completo, sin acoplar extensiones a internos del engine.

Programa completo: modulos.rs. Workflow: saludo.json.

5. Decidir por datos y capturar errores

Un conector HTTP saliente entrega {status, body} cuando obtiene una respuesta JSON válida. Un 404 o un 500 es un dato que el workflow debe interpretar. Un fallo de transporte o de validación es un error. Este ejemplo usa respuestas locales: permite aprender esas rutas sin conectarse a una API real.

EntradaSalida
{"status":200,"body":{"nombre":"Ada"}}{"resultado":"encontrado"}
{"status":404,"body":null}{"resultado":"ausente"}
{"status":429,"body":null}{"resultado":"posponer"}
{"status":500,"body":null}{"resultado":"revisar_status"}
{"body":null}{"resultado":"entrada_incompleta"}

decision.when consume un booleano. No interpreta expresiones como status == 200. La salida del control tiene selected y output; el binding /output permite que el host reciba solo el resultado de negocio.

El documento incluye un catch específico para mapping.missing. Su fallback obligatorio atiende otros errores capturables. El programa también prepara una variante sin fallback de decision: un status 500 produce control.no_match y comprueba la salida general error_no_previsto. Para tu módulo puedes declarar códigos como cliente.no_disponible y capturarlos con el mismo mecanismo. Cada handler recibe {input, error}; puedes usar bindings sobre ese sobre para conservar detalles, evitando exponer secretos al consumidor.

La entrada del ejemplo es deliberadamente permisiva para mostrar un campo ausente dentro del cuerpo. En una API de aplicación normal, define un schema estricto: los errores de admisión ocurren antes del cuerpo y regresan al host. Cancelación, límites, errores internos y efectos inciertos tampoco se convierten en una salida exitosa por un fallback.

La salida posponer solo comunica una decisión; no agenda trabajo futuro ni activa un reintento oculto. Los intentos y backoff se configuran por las políticas del motor. Ver errores y efectos.

Programa completo: respuestas.rs. Workflow: respuestas.json.

6. Componer una importación con resultados parciales

Ahora combina controles y una extensión: un lote acotado de clientes ejecuta el subworkflow de saludo para cada elemento. Se registra el hijo por ID y revisión antes de preparar el padre. El ejemplo permite elementos heterogéneos en el schema raíz para mostrar un error de validación del hijo por elemento.

ÍndiceResultado
0succeeded · {"saludo":"Hola, Ada"}
1failed · error estructurado de schema del subworkflow
2succeeded · {"saludo":"Hola, Rafael"}

El programa también verifica que un lote vacío devuelve []. collect conserva errores conocidos por elemento; no convierte un efecto incierto en un fallo ordinario. Si la respuesta global es Ok(array), el host todavía debe revisar los estados de cada elemento antes de marcar toda la importación como exitosa.

Composite: el subworkflow reutiliza un contrato y una revisión. No crea un servicio ni un run independiente. Si solo necesitas agrupar pasos una vez, un cuerpo inline basta. Para enriquecer desde dos fuentes, revisa parallel y el ejemplo controles; la concurrencia de ramas no implica orden temporal de efectos.

Programa completo: importacion.rs. Workflow: importacion.json.

7. Integrar un archivo sin meter sus bytes en JSON

Cuando tu aplicación recibe un archivo, publica el stream como artefacto y vincula su referencia al run. El workflow transporta la referencia; los bytes los administra el proveedor seleccionado por el host.

El programa completo publica un CSV pequeño, devuelve su referencia y verifica los bytes leídos. No afirma parsear ni importar el CSV: ese siguiente paso requiere registrar el conector correspondiente, explicado en recursos. Define tamaño máximo y retención; no conviertas una descarga ilimitada en un Vec.

Programa completo: artefactos.rs. Workflow: archivo.json.

8. Cuando necesitas recibos, deduplicación o señales

Usa execute para una llamada que pertenece al caller. Cambia a start/wait cuando tu aplicación necesita conservar un RunId, deduplicar entregas o relacionar una señal con una ejecución. El host mantiene responsabilidad explícita sobre su seguimiento y cancelación.

NecesidadReceta existenteResponsabilidad del host
Volver a recibir el mismo mensajeSQLite y recibosUsar una clave estable, revisar garantía durable y ventana de deduplicación.
Esperar una aprobaciónReservas y señalesReservar antes de despachar, correlacionar y autenticar la respuesta, definir timeout.
Reanudar tras reiniciarRecuperación explícitaElegir RecoveryPolicy::Resume, conservar revisiones y store, respetar deadlines originales.

Ejecuta el comando dos veces con la misma entrada y clave para observar la deduplicación dentro de su retención. Usa una ruta de demostración propia y un solo dueño del store. El arranque predeterminado rechaza trabajo inconcluso; no reanuda silenciosamente.

La demostración de señales entrega el mensaje desde el mismo host. Un callback real requiere tu transporte y autenticación. Una espera sigue estando acotada y el motor solo vive mientras su aplicación lo conserva.

Qué cambia al llevarlo a tu aplicación

Conserva el patrón de arranque y cierre; sustituye las entradas locales por tus DTOs. Inyecta clientes y recursos en las operaciones. Mantén las decisiones y el mapping declarativos en el workflow, y aplica autenticación y política de carga en el host. Empieza con memoria para comportamiento; elige persistencia solo si necesitas sus garantías.

Los ejemplos ejecutables comprueban su salida con assertions y cubren bordes concretos. Son demostraciones locales, no aceptación de integraciones reales ni mediciones de capacidad. Consulta límites y diagnóstico antes de definir presupuestos para tu carga.
