Límites, diagnóstico y pruebas

Configura presupuestos, interpreta estados y comprueba tus extensiones con casos esenciales y fallos relevantes.

Configurar límites antes de boot

LímiteQué acotaDefault actual
active_runs / pending_runsRuns activos y admitidos pendientes.32 / 128
concurrent_attemptsLlamadas simultáneas a operaciones entre todos los runs.32
value_bytes / run_bytesTamaño de un valor JSON / datos retenidos contabilizados por run.1 MiB / 16 MiB
terminal_runs / retention_msRetención por cantidad y por edad.1000 / 1 hora
receipt_count / receipt_ttl_msReservas de deduplicación de recepción.10000 / 1 hora
attempt_timeout_ms / run_timeout_msDeadline de intento / run.30 s / 5 min
group_concurrency / active_scopesConcurrencia de grupo / cuerpos hijos activos.32 / 128
foreach_items / loop_iterations / activationsElementos / vueltas / activaciones totales del run.10000 / 1024 / 10000
wait_timeout_ms / signal_bytesTimeout máximo de espera / payload de señal.24 h / 64 KiB

Las cuotas de JSON no son una cota del RSS del proceso. También consumen memoria planes, resultados retenidos, clientes, buffers, runtime y allocator. Para un host de 512 MB, no multipliques una tasa medida por RAM ni asumas que los defaults garantizan caber: ajusta presupuesto y carga.

admission.full informa saturación antes de aceptar otro run. Un límite de datos puede producir resource.limit en una ejecución ya aceptada. No ocultes rechazos aumentando cuotas sin conocer la carga.

Interpretar el estado antes de responder

EstadoLectura operacional
Accepted / RunningTrabajo aceptado / en ejecución.
WaitingSuspendido por timer o señal; necesita su evento o deadline.
BlockedNo puede continuar sin resolver dependencia o incertidumbre.
CancellingCancelación solicitada; aún se clasifica el trabajo activo.
SucceededSalida final confirmada.
Failed / CancelledTerminación sin éxito; revisar error e incertidumbre conservada.

start devuelve aceptación. wait devuelve un snapshot al terminar o bloquearse; no garantiza Succeeded. result devuelve el output, un error de la ejecución o not_ready. Una consulta después de la retención puede devolver not_found.

Permisos y observación

AccessContext lo construye el host después de autenticar al llamante. AccessContext::trusted("default") es adecuado para los ejemplos y un host que controla sus entradas; no copies actor, scope, permisos o grants desde el JSON de negocio sin validar.

La primera topología tiene un scope por instancia y plugins compilados confiables. Esos permisos no son una sandbox para código Rust malicioso.

Un ExecutionObserver recibe eventos identificados para métricas y logs. Sus colas/plazos están acotados y pueden perder eventos. Las decisiones operativas se toman con el estado confirmado; no se infiere progreso durable de un log.

Comprobar lo esencial al agregar una capacidad

  1. Un recorrido válido: input y output exactos, usando el módulo a través de la fachada.
  2. Config/input inválidos: rechazo en el punto correcto y ninguna llamada al destino durante prepare.
  3. Recursos y límites: acceso denegado, tamaño excesivo y concurrencia relevante para el módulo.
  4. Si escribe: respuesta perdida, certeza correcta, clave estable y ausencia de retry inseguro.
  5. Si requiere durabilidad: recuperar después de una caída sin repetir pasos confirmados y con las revisiones necesarias.
  6. Apagado: cierre explícito, reporte de pendientes y comportamiento de handles detenidos.

Ejecuta las pruebas del módulo y los casos borde que cambiaste. Una campaña de rendimiento es opcional cuando hay una pregunta concreta de capacidad; no es el paso predeterminado para cada cambio documental o integración.

El kit de conformidad comprueba contratos de proveedores, y las pruebas de fronteras de fallo muestran inyección mediante puertos públicos.
