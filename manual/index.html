From one call to a composed integration

A practical guide to embedding the engine in your existing Rust system, with explicit ownership, data flow and bounded execution.

Ownership and boundaries

Embed Workflow Forge in your existing Rust backend, desktop application or worker. Your host configures resources and authenticates incoming work. Workflows choose order, data mappings and business routes. Operations adapt existing functions or SDKs and return facts or structured errors.

Keep the runtime alive while the host needs it. Share application handles, not runtime ownership. Prepare a definition once and reuse its plan for different inputs within the same composition. Plugins are trusted compiled Rust; they are not isolated processes or dynamically loaded scripts.

1. Your first embedded call

Use the pinned Rust toolchain. The project is preparing its first public release; the dependency below uses a neighboring checkout. Create src/main.rs and workflows/normalizar.json in your application.

Save this complete workflow as workflows/normalizar.json. It accepts a string and calls forge.text.trim. Input " Rafael " produces "Rafael".

The outcome block preserves execution errors until shutdown has been attempted. Check forced and pending; a dropped handle is not a substitute for an awaited close. The demonstration ends after one call; a real host keeps the instance for its application lifetime.

2. Share a facade inside your application

Store a small domain facade in your existing application state. Controllers or workers clone it and pass their authenticated context, data and a per-call cancellation token. Keep the engine runtime in the startup/shutdown owner. No additional web framework is necessary.

The complete example uses buffer_unordered(2) to keep two futures in flight, then restores input order by index. It checks Ada, Rafael and Grace independently. This per-batch bound does not replace the engine’s global quotas. Apply host backpressure on admission.full; do not build an unbounded queue or hold a mutex around every call.

Facade hides plan selection behind a domain method. Builder assembles providers before activation. A new trait is unnecessary unless your host actually needs multiple implementations. AccessContext::trusted is an explicit trust decision for local examples, not a context to accept from untrusted JSON.

Complete source: sistema.rs.

3. Cancel and bound calls

Use one child token per call. A disconnect or user action can cancel that child; a parent token can cancel a whole host scope. The requested timeout cannot exceed the configured run budget.

The program uses a five-second timer: one call is cancelled after 20 ms; another receives a 20 ms run deadline. It checks operation.cancelled and operation.timeout. Those times illustrate budgets, not guaranteed response latency.

Dropping an execute future also requests cancellation, while acceptance and cleanup remain supervised. Before host exit, stop admitting input, cancel or await owned calls, await shutdown and inspect its report. Rust operations must cooperate and avoid blocking executor threads or leaving unowned tasks.

Complete source: cancelacion.rs.

4. Adapt an existing capability

The greeting extension depends on the public protocol. It exports an OperationBundle with schemas, exact revision and effect/repetition declarations. The host registers it before build:

Input {"nombre":" Rafael "} produces {"saludo":"Hola, Rafael"}. These are example domain keys; they are not engine keywords. Existing fixture names and payloads remain stable.

Adapter: hold your SDK/client in the operation struct, translate invocation data and map output/error into public types. Reuse clients instead of reconnecting per invocation. The greeting is Pure/Safe because it only builds a string; do not copy those guarantees onto a remote write. Operations do not decide the next node.

For extension versioning, transparent decorators and provider strategy boundaries, read design patterns.

Complete source: modulos.rs. Definition: saludo.json.

Bindings and control reference

Every binding has exactly one constructor: literal, select, object or array. Select reads the current body input or a confirmed local predecessor. JSON Pointer "" selects the whole value; missing and null remain distinct. No string becomes executable code.

ControlResult / rule
decisionFirst true boolean case; returns selected + output.
parallelNamed branches; results keyed by branch, with explicit concurrency and join.
foreachBody receives item, index, context; output retains input index order.
loopBody replaces state; max_iterations bounds repetition.
subworkflowExact child revision, separate scope in the same root run.
timerAbsolute wake-up deadline; returns its input.

The controles program checks these shapes. A successor reads a control’s public output, not a sibling’s private node. The contracts specify schemas, scopes, limits, missing-value fallback and error handling in detail.

Complete source: controles.rs.

5. Route data and handle errors

A valid HTTP JSON response is data: {status, body}, including 4xx/5xx. A transport, content or validation failure is an error. This recipe supplies local responses, so it requires no real API connection.

InputChecked business result
status 200{"resultado":"encontrado"}
status 404{"resultado":"ausente"}
status 429{"resultado":"posponer"}
status 500{"resultado":"revisar_status"}
Missing status{"resultado":"entrada_incompleta"}

forge.data.equals compares {left, right} and returns a boolean for decision.when. There is no expression DSL such as status == 200. The decision output is {selected, output}; selecting /output exposes the business value.

The definition catches mapping.missing explicitly. Its required try fallback handles other eligible errors. The program also prepares a variant without a decision fallback: status 500 produces control.no_match, proving the generic error_no_previsto route.

Handlers receive {input, error} and return a body output. A failure inside a handler propagates outward. Admission errors occur before the workflow body; cancellation, global deadlines, quotas and unknown effects also cannot be hidden as success. The example permits a missing status deliberately; use a strict application input schema when that is your contract.

Returning “postpone” communicates a result; it does not schedule a background retry. Read outcome semantics and outbound connector contracts before adapting this to real HTTP.

Complete source: respuestas.rs. Definition: respuestas.json.

6. Compose a batch with partial failures

Register the greeting module and its child workflow, then prepare the parent import. The parent accepts at most 20 records, executes two iterations concurrently and collects known failures. Its deliberately broad item schema lets the child validate each record.

The result contains success for indices 0 and 2, and a structured schema failure for index 1. The program also checks an empty input produces []. An Ok(array) does not mean every item succeeded: inspect item states. collect never turns an uncertain write into an ordinary failed item.

Composite: the child reuses a contract and revision within the root run. Use an inline body for a one-off grouping. If effects need a strict order, choose concurrency 1 or explicit partitioning in the host/domain adapter.

Complete source: importacion.rs. Definition: importacion.json.

7. Pass files by reference

Publish an input stream as an artifact and declare its reference when accepting the run. JSON carries metadata; the provider owns bytes and retention.

The program publishes a small CSV, passes its reference through a workflow and checks the downloaded bytes. Parsing is a separate operation. The inventory proof of concept adds CSV batches, domain writes and a report. Bound file size and retention; do not collect unlimited streams into a Vec.

Complete source: artefactos.rs. Definition: archivo.json.

The default composition uses memory. Enable sqlite for a durable provider, integrations for HTTP/files/CSV constructors, or full for both. Features do not register endpoints or choose providers automatically. For durable artifact ownership, install the same SQLite instance behind both execution and artifact ports.

8. Receipts, recovery and signals

Use execute for work owned by a caller. Choose start/wait for retained run IDs, deduplicated deliveries and external signals; then the host explicitly owns tracking and cancellation. Acceptance and completion are separate guarantees.

Repeat with the same input/key to observe deduplication within its retention window. Use your own demonstration path and one database owner. Default boot rejects unfinished work; explicitly select RecoveryPolicy::Resume to recover it under original deadlines and revisions.

For approvals, await_signal reserves a wait before optional external dispatch. The host delivers a SignalCommand with run/wait/message identity, correlation and payload. Authentication belongs to the host. Unknown reservation, conflicting duplicate and expired wait are distinct failures; a callback does not resolve an uncertain start effect.

Complete source: senales.rs. Definition: aprobacion.json.

The local signal demo needs no transport. The two-process-start example closes and reopens the same SQLite store sequentially. Neither example is a distributed worker system or permission to execute indefinitely.
